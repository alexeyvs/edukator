# Edukator: админка оператора

## Overview

Приложение перестало быть домашним: `deploy.sh` ставит его systemd-сервисом на
VPS, и в `control.db` живут чужие семьи. У оператора нет ни одного способа узнать,
что там происходит, кроме ssh и `sqlite3` руками.

План строит админку оператора: четвёртый предъявитель `admin` со своим входом,
имперсонацию чужой семьи **в режиме только чтения** с двумя независимыми замками
на запись, трёхслойную статистику и собственное хранилище аварий вместо journald.

Утверждённая спека: `docs/superpowers/specs/2026-08-21-edukator-admin-design.md`.
Многоарендность: `docs/plans/20260819-edukator-multi-tenancy.md`.
Основная спека: `docs/superpowers/specs/2026-08-07-edukator-design.md`.

**Не входит:** второй фактор (место оставлено — вход разложен так, что шаг
вставляется без переделки маршрутов); роли и разные права у разных операторов;
любое редактирование чужих данных из админки; экспорт; ретеншен логов по времени;
счётчик забракованных генераций; графики — таблицы и числа; HTTP-журнал запросов
и события codex в логах.

## Context (from discovery)

- Ветка `worktree-multi-tenancy` от `develop`. Многоарендность уже на месте:
  `control.db` версии 1 с семью таблицами, три предъявителя, ленивый реестр
  арендаторов.
- **`server/auth.ts` (415 строк)** — `resolveBearer` разбирает предъявителя в
  жёстком порядке (детская cookie → `ACTOR_COOKIE` → агентский заголовок →
  родительская cookie), `authorizeChild` сверяет принадлежность **одной выборкой**
  до открытия базы, `resolveTenant` собирает всё вместе. `isMutating` и
  `assertSameOrigin` уже дают предикат «запрос меняет состояние», которым
  пользуется проверка источника.
- **`server/routes/tenant-context.ts`** — матрица `ROUTE_ACCESS` (`child`, `gate`,
  `dashboard`), `allow` обязателен у каждого маршрута,
  `tests/tenant-context.test.ts` сверяет свою таблицу с `onRoute` поимённо.
- **`TenantOpener.open(childId, bearer)`** получает вид предъявителя не ради
  открытия, а ради будильника прогрева (`dispatcher.wake` только на `browser`).
- **`server/control-db.ts`** — `CONTROL_SCHEMA_VERSION = 1`, `migrateControl`
  внутри `transaction(...).immediate()` с перечитыванием `user_version`,
  `CONTROL_TABLES` сверяется тестом, `login_attempts.kind` ограничен
  `CHECK (kind IN ('password', 'pin'))`.
- **Логов нет вовсе:** `Fastify({ logger: false })` (`server/index.ts:203`),
  подробности ошибок уходят `process.stderr.write` из `setErrorHandler`, на VPS их
  забирает journald. `console.error` в `server/` и `scripts/` не встречается ни
  разу.
- **`server/routes/token-privacy.ts`** — `redactTokenUrl` уже заменяет сегмент
  токена на `<token>` в том, что уходит в stderr.
- **`server/backup.ts`** открывает детские базы голым `better-sqlite3` в
  `readonly` — то есть readonly-обход детских баз в проекте уже работает.
- **`APP_PAGES`** (`server/index.ts:84`) — `['/', '/parents', '/join/:token',
  '/invite/:token']`, покрыт тестом; забытый адрес даёт 404 статики, а не поломку
  сборки.
- **`web/src/App.tsx`** держит четыре состояния (страница по ссылке, никто не
  вошёл, родитель, ребёнок); с админкой их станет шесть, а имперсонация ложится
  поперёк как признак.
- **Пороги покрытия** в `vitest.config.ts` заданы поимённо; новые модули не
  попадут ни под один шаблон.
- **`scripts/parent.ts`** читает секреты со stdin через `createSecretReader` —
  один `readline` на запуск, закрытый stdin даёт отказ, а не молчаливый успех.

## Development Approach

- **Testing approach**: TDD для чистой логики (разрешение админского
  предъявителя, оба замка имперсонации, ротация и разбор хвоста лога, агрегация
  статистики, выбор состояния клиента). Для схемы, маршрутов, скриптов и I/O
  допустим обычный порядок — ровно как записано в `CLAUDE.md`.
- **Ни один тест не вызывает настоящий codex.** Шим `codex` в `PATH` и проверка
  отсутствия маркера вызова остаются во всех e2e.
- Комментарии, тексты ошибок и названия тестов — по-русски. Комментарий объясняет
  *почему*, а не *что*.
- Каждая задача доводится до конца перед переходом к следующей.
- **КРИТИЧНО: каждая задача обязана содержать новые или обновлённые тесты** для
  изменённого в ней кода — и на успешный путь, и на ошибочный. Тесты не
  опциональны, это часть чеклиста.
- **КРИТИЧНО: все тесты обязаны проходить до начала следующей задачи.**
- **КРИТИЧНО: план обновляется, если по дороге меняется объём работы.**
- Схема **детской** базы не меняется ни в одной задаче. Это свойство держится
  намеренно: админка не трогает ни одной доменной таблицы.

## Testing Strategy

- **Unit-тесты** — обязательны в каждой задаче.
- **Калибровочные числа** — с буквальным тестом: тест, строящий ожидание из той
  же константы, её подмену не ловит.
- **Два замка имперсонации проверяются по отдельности.** Тест, остающийся зелёным
  после снятия любого одного из них, не держит ничего: весь смысл второго замка в
  том, что он переживает забытый флаг.
- **E2E** (Playwright) — один сценарий «оператор» в задаче 21; изменения UI и
  HTTP-контрактов требуют `npm run test:e2e` по правилу проекта.
- **Покрытие** — 80% пофайлово, пороги прописываются поимённо в задаче 22.

## Progress Tracking

- Отмечать выполненное `[x]` сразу, а не пачкой.
- Новые обнаруженные задачи — с префиксом ➕.
- Помехи и блокировки — с префиксом ⚠️.
- Расхождение с замыслом записывать разделом «Где реализация разошлась с

## Technical Details

**Новые таблицы `control.db`** (версия 2):

| Таблица | Ключевое |
| --- | --- |
| `admins` | `email` уникальный в нижнем регистре, `password_hash`, `credentials_changed_at`, `disabled_at` |
| `admin_sessions` | `token_hash`, `last_seen_at`, `expires_at`, `revoked_at` |
| `admin_impersonations` | `child_id`, `role` (`browser`/`parent`), `token_hash`, `expires_at`, `revoked_at` |
| `admin_audit` | `admin_id`, `at`, `action`, `child_id`, `parent_id`, `detail` |
| `login_attempts` | пересоздана: `kind` получил третье значение `admin` |

**Четвёртый предъявитель:** `admin` — cookie `__Host-edu_admin`,
`SameSite=Strict`, строка матрицы `admin: ['admin']`. Аренды у админских
маршрутов нет, поэтому их разрешает отдельный `createAdminContext`, а не
`resolveTenant`: приоритет имперсонации иначе вернул бы на `/api/admin/*`
предъявителя `browser`, и админка отказывала бы ровно тогда, когда оператор в
имперсонации и хочет из неё выйти.

**Имперсонация:** cookie `__Host-edu_impersonation`, живёт рядом с админской.
`resolveBearer` возвращает обычного `browser`/`parent` целевой семьи плюс поле
`impersonation`. Два независимых замка: отказ по `mutating` в `resolveTenant` и
`PRAGMA query_only = ON` на отдельном соединении.

**Слои статистики:** 1 — только `control.db`, мгновенно; 2 — обход детских баз по
одной в `readonly` с кешем; 3 — одна названная база по требованию.

**Журнал:** `<каталог данных>/logs/app.jsonl`, ротация по размеру, чтение хвостом.

**Константы:**

| Константа | Значение |
| --- | --- |
| `MIN_ADMIN_PASSWORD_LENGTH` | 16 |
| `ADMIN_SESSION_IDLE_MS` | 30 минут |
| `ADMIN_SESSION_MAX_MS` | 8 часов |
| `IMPERSONATION_TTL_MS` | 15 минут |
| `ADMIN_STATS_TTL_MS` | 5 минут |
| `LOG_MAX_BYTES` | 8 МБ |
| `LOG_KEEP_FILES` | 4 |
| `LOG_TAIL_BYTES` | 512 КБ |
| `ADMIN_LOG_PAGE` | 200 |

## Post-Completion

*Требует ручного вмешательства или внешних систем — без чекбоксов.*

**Ручная проверка:**

- завести оператора на боевой машине через `npm run admin -- create` и убедиться,
  что вход работает по https с настоящей cookie `__Host-`
- зайти имперсонацией в собственного ребёнка и убедиться, что баннер виден, а
  «ответить» отказывает
- убедиться, что после суток работы `logs/` не превысил 32 МБ

**Риски, названные, но не закрытые:**

- один пароль открывает данные всех семей сразу — второго фактора в этой работе
  нет
- имперсонация показывает содержание чужого ребёнка; сдержана только аудитом и
  15-минутным TTL
- открытый экран статистики читает все детские базы раз в пять минут
