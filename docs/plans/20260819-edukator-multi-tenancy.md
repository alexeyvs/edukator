# Edukator: базовая многоарендность

## Overview

Приложение сегодня однопользовательское по построению: `buildServer` открывает
единственную базу при старте и держит соединение в замыкании, `profile` — одна
строка, родительский PIN лежит в переменной окружения, аутентификации нет вовсе.
Этого хватает домашней сети и не хватает, как только сервер доступен снаружи.

План строит базовую многоарендность: родитель заводится по email и паролю (закрытым
списком, через скрипт), ведёт нескольких детей, каждый ребёнок входит со своего
компьютера по одноразовой ссылке и занимается **в своей отдельной базе**. Плюс
честная очередь фоновой генерации между детьми, без которой второй ребёнок ломает
занятие первому.

Утверждённая спека: `docs/superpowers/specs/2026-08-19-edukator-multi-tenancy-design.md`.
Основная спека: `docs/superpowers/specs/2026-08-07-edukator-design.md`.

**Не входит:** настройка TLS/секретов/бэкапов на хостинге, Windows-агент вместо
Python-контроллера, переход codex на API-ключ, самостоятельная регистрация
родителей и восстановление пароля почтой, общий банк заданий между детьми.

## Context (from discovery)

- Ветка `worktree-multi-tenancy` от `develop` (5fcd096). Базовый прогон чист:
  60 файлов, 1127 тестов.
- **`buildServer` (`server/index.ts`)** открывает базу один раз через
  `openSessionDatabase`, снимает отпечаток inode (`fileIdentity`) и раздаёт
  соединение всем `register*Routes` вместе с `available`. При недоступности базы
  регистрируются `registerUnavailable*` — то есть состав маршрутов выбирается на
  старте навсегда.
- **`registerSessionRoutes` (`server/routes/session.ts`)** держит в замыкании не
  только базу: `reviewing` (:142), `pendingReviews` (:143), `retryTimers` (:144),
  восстановление незакрытых споров `openDisputes(db)` (:399) и ожидание их
  завершения (:412). Это состояние **на арендатора**, а не на процесс.
- **PIN** сегодня — `EDUKATOR_PARENT_PIN` через `readParentPin`, проверяется
  `verifyParentPin` (SHA-256 + `timingSafeEqual`) и защищает ровно два маршрута:
  `PUT /api/parents/computer-access` и
  `PUT /api/parents/runs/:runId/integrity/:itemId/approve`.
- **Бюджет codex** — два процессных объекта `codexConcurrency` (2 места) и
  `disputeConcurrency` (1 место). `budget.run` в воркере (:243) оборачивает
  `produce`, внутри которого генерация **и** проверка, до трёх заходов — то есть
  один «слот» это 2-6 настоящих вызовов `runCodexCli`.
- **Воркер** (`server/codex/worker.ts`) за один `runWarmupCycle` готовит босса,
  доливает все голодные темы до `QUEUE_TARGET` параллельным пулом и готовит
  персональные материалы. `WorkerHandle` умеет только `stop()` (:474).
- **Статика**: сервер отдаёт `index.html` явно только для `/parents`
  (`server/index.ts:552`); прочие пользовательские адреса ушли бы в 404.
- **Пороги покрытия** в `vitest.config.ts` заданы поимённо (:15-81); новые модули
  не попадут ни под один шаблон.
- **Контроллер** (`controller/`) ходит в `gate/status` без авторизации, опрашивает
  раз в 20 секунд (`config.py:21`); `npm test` гоняет только Vitest и его правок
  не увидит.
- **E2E** поднимают `buildServer` внутри процесса на временной базе; `npm start`
  запрещён.

## Development Approach

- **Testing approach**: TDD для чистой логики (KDF и разбор секретов, политика
  допуска, порядок разрешения аренды, фазы диспетчера, резерв квоты). Для
  каркаса, схемы, скриптов и I/O допустим обычный порядок — ровно как записано в
  `CLAUDE.md`.
- **Ни один тест не вызывает настоящий codex.** Шим `codex` в `PATH` и проверка
  отсутствия маркера вызова остаются во всех e2e.
- Комментарии, тексты ошибок и названия тестов — по-русски. Комментарий объясняет
  *почему*, а не *что*.
- Каждая задача доводится до конца перед переходом к следующей.
- **КРИТИЧНО: каждая задача обязана содержать новые или обновлённые тесты** для
  изменённого в ней кода — и на успешный путь, и на ошибочный. Тесты не
  опциональны, это часть чеклиста.
- **КРИТИЧНО: все тесты проходят до начала следующей задачи.** Исключений нет.
- **КРИТИЧНО: план обновляется, если объём меняется по ходу.**
- Обратная совместимость **не** требуется: беспарольный режим убирается
  сознательно (см. спеку, «Почему беспарольного режима не остаётся»).

## Testing Strategy

- **Юнит-тесты**: обязательны в каждой задаче (см. выше). Один файл на модуль,
  имена совпадают, временные базы через `mkdtempSync`.
- **E2E (Playwright)**: сценарии поднимают `buildServer` сами. Меняются UI и
  HTTP-контракты, поэтому e2e переписываются в задачах 20-21 и должны проходить
  до задачи проверки соответствия.
- **Контроллер**: у него отдельный гейт `npm run family:test` (pytest в его
  окружении) — `npm test` его правок не видит.
- Тест, проходящий и после порчи проверяемого кода, не считается тестом:
  сомневаетесь — испортите строку в `server/` и убедитесь, что он покраснел.

➕ Cookie отдаётся двумя способами, и оба обязательны. Браузеру она ставится
самим помощником (`context` и `signIn` в настройках), а для запросов мимо
интерфейса он отдаёт заголовок `cookieHeader(side)`: `page.request` ходит не
браузером, а узлом, и cookie с `Secure` по голому http не носит — хотя сам
Chromium 127.0.0.1 доверенным источником считает. Снять `Secure` нельзя: без
него браузер не примет cookie с префиксом `__Host-` вовсе. Тому же `page.request`
приходится выставлять `Origin` руками — на изменяющем запросе он его не шлёт, и
сервер отказал бы такому запросу как неподтверждённому.

сценарий, который её и гасит.

➕ Сценарий с PIN назван по тому, что PIN в системе вообще подтверждает:
«забракованного вопроса», который родитель подтверждал бы с детской машины, в

проверяет обе стороны этого правила: с детской машины неверный PIN отвергается

спрашивается вовсе.

## Technical Details

**Схема `control.db`** (своя версия, своя миграция):

| Таблица | Ключевое |
| --- | --- |
| `parents` | `email` уникальный в нижнем регистре, `password_hash`, `pin_hash`, `credentials_changed_at`, `disabled_at` |
| `parent_invites` | `token_hash`, `expires_at`, `used_at` |
| `parent_sessions` | `token_hash`, `last_seen_at`, `expires_at` |
| `children` | `status` (`provisioning`/`ready`/`failed`), `last_activity_at`, `retired_at`; **пути базы нет** |
| `child_devices` | `kind` (`browser`/`agent`), `invite_hash`, `claimed_at`, `token_hash`, `revoked_at` |
| `codex_quota` | `child_id`, `day` (Москва), `calls` |
| `login_attempts` | счётчики по email и по адресу |

**Три предъявителя:** `parent` (cookie `__Host-edu_parent`, `SameSite=Strict`),
`browser` (cookie `__Host-edu_child`, `SameSite=Lax`), `agent` (заголовок, только
`GET /api/gate/status`).

**Порядок разрешения запроса:** предъявитель → проверка принадлежности одной
выборкой → открытие базы. Не наоборот.

**Единица квоты:** один `runCodexCli`, не один `budget.run`.

**Константы:** `CODEX_DAILY_QUOTA = 60`, срок сессии 30 дней бездействия при
потолке 90, приглашение живёт 48 часов, детский cookie — десять лет при серверном
выключателе `revoked_at`.
