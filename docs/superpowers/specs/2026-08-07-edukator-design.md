# Edukator — дизайн

Дата: 2026-08-07

## Задача

Ребёнок 13 лет идёт в 7 класс, учится на 3-4. Семья меняет школу. Для поступления
нужно сдать вступительные тесты по русскому языку, английскому языку и математике
**минимум на 4**.

Нужно веб-приложение, которое:

- автоматически выявляет пробелы в знаниях и концентрируется на них;
- укладывается в **40 часов чистого времени** ученика;
- показывает родителям актуальную ситуацию по обучению;
- не вызывает отторжения у подростка: саркастичный тон, задачи из его мира,
  измеримый прогресс.

## Ограничения

| Ограничение | Значение |
|---|---|
| Дедлайн | **25.08.2026** — 18 дней от 7 августа |
| Бюджет времени ученика | 40 часов на три предмета |
| Темп занятий | ~2 часа в день |
| Срок разработки MVP | 3-5 дней, заниматься можно с 3-го дня |
| Что известно о тестах | только название школы; «ничего необычного» |
| Хостинг | локально на домашнем маке, доступ по локальной сети |
| LLM | codex CLI 0.146.0 (подписка, не API-ключ) |
| TTS | ElevenLabs, ключ в `ELEVENLABS_API_KEY` |

Производная рамка: 2400 минут = **94 забега** по 25 минут ≈ **1200 заданий**.
При 18 днях до экзамена это **5-6 забегов в день**, то есть чуть больше двух
часов ежедневно без пропусков. Запаса нет: пропущенный день стоит примерно двух
тем.

Тем в трёх учебниках существенно больше, чем помещается в этот бюджет, поэтому
приоритизация тем — не украшение, а ядро системы. Замер планировщика на
собранных картах показывает, что при 50-60% верных ответов 3-5 тем с
`exam_weight ≥ 2` останутся незакрытыми (см. раздел «Планировщик»).

**Что известно об ученике:** слабый предмет — русский язык (по оценкам за 6
класс). Конкретные проблемные темы неизвестны, их находит триаж. Интересы для
генерации сюжетов задаются в профиле при первом запуске.

## Источники содержания

Карта тем строится из трёх учебников за 6 класс (скачаны в `~/Downloads`):

- математика — Мерзляк, базовый уровень;
- русский язык — поурочные планы по учебникам Баранова / Разумовской;
- английский язык — New Millennium English, Деревянко и др.

Извлечение оглавлений и тематических перечней в JSON — **разовый шаг сборки**
с помощью codex и последующей ручной проверкой. В рантайме учебники не участвуют.

## Измерения, на которых основан дизайн

Замеры сделаны 2026-08-07 на рабочей машине:

| Что | Результат |
|---|---|
| `codex exec`, тривиальный промпт, gpt-5.6-sol, low | 15.5 с |
| То же, gpt-5.6-terra | 9.7 с, инструкция соблюдена |
| То же, gpt-5.6-luna | 9.8 с, вернул болванку вместо задачи |
| Батч из 5 заданий с hint/explain/joke, terra, low, `--output-schema` | **23.6 с** (≈4.7 с на задание) |

Качество батча: все 5 ответов арифметически верны, регистр юмора соответствует
возрасту; 2 задания из 5 логически натянуты («вычел −13 баллов за выполненное
задание»). Отсюда — обязательный валидационный проход.

Рабочая модель — **gpt-5.6-terra**, запасная — luna.

**Обнаруженный подводный камень:** без `< /dev/null` codex считает, что stdin
пайпится, и ждёт EOF бесконечно. Все вызовы обязаны закрывать stdin.

## Форма приложения

Рассмотренные варианты: бесконечная лента заданий; короткие сессии с рамкой;
сюжетная игра с картой мира. Выбран **вариант с забегами**: бесконечная лента не
даёт чувства завершённости, сюжетная игра стоит лишней недели разработки, не
двигая оценку.

**Забег** = 20-25 минут = один предмет = ~12-15 заданий с явной целью и финальным
экраном. День состоит из 2-3 забегов.

## Основной цикл

В приложении живёт **саркастичный ИИ-напарник** — единая персона на всё
приложение. Тон: старший брат, который сам это ненавидел, но знает, как сдать.
Не сюсюкает, не хвалит за тривиальное, язвит и в адрес школы, и в свой
собственный. При первом запуске представляется и предлагает себя переименовать.

1. Напарник объявляет цель забега.
2. Задание появляется **мгновенно** — оно уже лежит в тёплой очереди.
3. Ученик отвечает. Проверка **детерминированная**, без обращения к LLM.
4. Верно → саркастичная реакция и XP. Неверно → разбор (сгенерирован заранее
   вместе с заданием) и постановка темы на повтор.
5. Кнопка **«я всё-таки прав»** — спорный случай уходит в фоновую перепроверку
   через LLM; при подтверждении баллы возвращаются задним числом, а `accept[]`
   задания пополняется.
6. Финальный экран: что закрыто, что просело, как сдвинулся прогноз оценки.

## Карта тем

Три статических файла `content/curriculum/{math,russian,english}.json`,
примерно по 20-25 тем на предмет.

Поля темы:

| Поле | Назначение |
|---|---|
| `id` | стабильный идентификатор |
| `subject` | math / russian / english |
| `title` | название обычными словами (попадает в дашборд родителей) |
| `exam_weight` | 0-3, вероятность встретиться на вступительном; главный рычаг приоритизации |
| `difficulty` | 1-3, базовая сложность |
| `prereqs[]` | темы, которые должны быть освоены раньше |
| `answer_format` | `number` / `text` / `choice` — определяет нормализатор ответа |
| `prompt_seed` | как генерировать задания по теме, с примерами формулировок |

`exam_weight` задан по типовой программе. Если школа опубликует демоварианты,
достаточно поправить веса — план пересобирается автоматически.

## Модель знаний

Намеренно простая и объяснимая: ни IRT, ни обучаемых моделей. Требование
объяснимости жёсткое — родителям придётся обосновывать прогноз, и «так решила
модель» негодный ответ.

По каждой теме хранятся `mastery` (0..1) и `confidence` (растёт с числом попыток,
затухает со временем).

- Верный ответ: `mastery += α·(1 − mastery)`; α выше для сложных заданий,
  ниже при использовании подсказки.
- Неверный ответ: `mastery -= β·mastery`; β выше для лёгких заданий, поскольку
  ошибка в простом задании информативнее.

Стартовые значения коэффициентов (подлежат калибровке по пробным экзаменам):

| Коэффициент | База | Множитель по сложности 1 / 2 / 3 | Прочее |
|---|---|---|---|
| α (верный ответ) | 0.35 | 0.7 / 1.0 / 1.3 | ×0.5 при использованной подсказке |
| β (неверный ответ) | 0.30 | 1.3 / 1.0 / 0.7 | — |

`confidence` растёт как `1 − 0.75^n` по числу попыток `n` и умножается на
затухание `0.98^d`, где `d` — дней с последней попытки по теме.

Источник тем — файлы `content/curriculum/*.json`; они истина в последней
инстанции. Таблица `topic_state` хранит только рантайм-состояние и связана с
темой по `topic_id`. При старте сервера отсутствующие темы заводятся в
`topic_state` с нулевыми значениями, а записи по исчезнувшим темам игнорируются.

**Пробелом** считается тема, у которой либо `mastery < 0.6` при достаточной
`confidence`, либо `exam_weight ≥ 2` и ни одной попытки. Второй случай
приоритетнее: непроверенная тема опаснее известной слабой.

## Планировщик

```
priority = exam_weight × (1 − mastery) × prereqs_ready × urgency
```

`urgency` растёт для тем, подошедших к интервальному повторению (чем выше
`mastery`, тем реже возврат), и резко растёт к дате экзамена для тем с большим
весом. Предмет дня выбирается так, чтобы отстающий получал больше забегов, но
не подряд.

**`prereqs_ready` — мягкий множитель, а не затвор 0/1:**

```
prereqs_ready = 1,                                          если все предпосылки ≥ 0.6
              = max(0.2, среднее(min(1, mastery_p / 0.6)))   иначе
```

Исходно множитель был двоичным, и это оказалось дефектом. Ноль обнулял приоритет
целиком, поэтому `urgency` не мог его перебить: тема с неосвоенным фундаментом не
всплывала никогда, сколько бы ни оставалось до экзамена. На собранных картах
цепочки предпосылок доходят до девяти уровней.

Замер сделан на реальном коде планировщика и реальных картах: 40 дней по три
забега, пять прогонов на каждом уровне успеваемости, 69 тем, из них 58 с
`exam_weight ≥ 2`.

| Точность ответов | Затвор 0/1 (не предложено / освоено) | Мягкий множитель |
|---|---|---|
| 50% | 11.0 / 33.4 | **5.4 / 40.4** |
| 60% | 4.8 / 48.8 | **3.2 / 50.6** |
| 75% | 1.4 / 55.6 | **0.0 / 57.0** |

Затвор бил тем сильнее, чем слабее ученик, — ровно наоборот нужному. Смягчение
вдвое сокращает пропуски и добавляет около семи освоенных тем при слабой
успеваемости.

**Пропуски при 50-60% не исчезают полностью, и это не дефект формулы.** Остаток —
нехватка бюджета: 120 забегов на 69 тем, часть которых уходит на интервальные
повторения. Лечится не планировщиком, а решением, что делать с темами, на которые
времени не хватает: снижать им `exam_weight` вручную либо принимать, что часть
программы останется незакрытой. Вопрос всплывёт на этапе 4, когда прогноз оценки
покажет это родителям.

Цена смягчения — принцип «сначала фундамент» слабеет, но сохраняется: неготовая
тема просаживается в приоритете пропорционально тому, насколько её предпосылки
не добраны. Пол 0.2 выбран по симуляции; значение 0.15 по результатам
неразличимо.

## Триаж

15 минут на предмет, ~12 заданий лесенкой: старт со средней сложности, верный
ответ повышает сложность, неверный понижает. За 45 минут на все три предмета даёт
грубое ранжирование тем — достаточно, чтобы первые дни не тратились вслепую.
Дальше модель уточняется каждым ответом.

Полная адаптивная диагностика (~40 минут на предмет) отвергнута: два часа из
сорока плюс демотивация от двух часов проваленных тестов на старте.

## Генерация заданий

### Вызов

```
codex exec --ephemeral --ignore-user-config --ignore-rules \
  --skip-git-repo-check --sandbox read-only --cd <temp> \
  -m gpt-5.6-terra -c model_reasoning_effort=low \
  --output-schema schemas/tasks.json -o <out.json> \
  "<промпт>" < /dev/null
```

### Промпт

Собирается из пяти частей: персона напарника, `prompt_seed` темы, профиль ученика
(имя, игры, стримеры, интересы), целевая сложность, последние 20 формулировок по
этой теме с указанием не повторяться.

### Схема ответа

Массив `items[]`, каждый элемент: `question`, `answer`, `accept[]` (допустимые
формы ответа), `hint` (не раскрывает ответ), `explain` (разбор на 2-3
предложения), `joke` (реакция на верный ответ), `difficulty`.

### Валидация

Отдельный второй вызов codex. Валидатор получает **только условия, без ответов**,
решает задания самостоятельно и дополнительно проверяет: условие однозначно,
ситуация не натянута, тема соответствует заявленной, содержание уместно для
подростка. Ответы валидатора сверяются с ответами генератора; расхождение или
любая проваленная проверка отправляют задание в мусор.

### Тёплая очередь

Таблица `task_bank` в SQLite. Воркер держит **≥8 провалидированных заданий** по
каждой из 3-5 тем, которые планировщик выберет ближайшими. Долив запускается при
падении ниже 4. Одновременно не более двух процессов codex.

### Устойчивость

Ученик никогда не видит спиннер. Три уровня защиты:

1. тёплая очередь;
2. фоновый долив с опережением (батч из 5 заданий покрывает 5-10 минут решения);
3. **посевной банк** — по ~30 проверенных заданий на предмет, сгенерированных
   заранее и закоммиченных в репозиторий.

При падении codex, исчерпании лимита подписки или потере сети занятие продолжается
на посевном банке; приложение только пишет в лог. Команда `npm run prefetch`
набивает банк на завтрашние темы (можно запускать на ночь).

## Проверка ответов

Без обращения к LLM. Нормализатор выбирается по `answer_format` темы:

- **number** — извлечение числового значения из строки и численное сравнение;
  `−45`, `-45` и `-45 монет` эквивалентны (юникодный минус обрабатывается явно);
- **text** — нижний регистр, схлопывание пробелов, ё=е, сверка с `accept[]`;
- **choice** — прямое сравнение.

Ответ приходит мгновенно. Ложные срабатывания разбирает кнопка «я всё-таки прав»:
спорный случай уходит в фоновую очередь на разбор через LLM, при подтверждении
баллы возвращаются задним числом и `accept[]` задания пополняется — банк
самоисправляется.

## Прогноз оценки

Центральная метрика, общая для ученика и родителей.

```
score = Σ(exam_weight_i × mastery_i) / Σ(exam_weight_i)     по темам с exam_weight ≥ 1
```

Отображение на пятибалльную шкалу — **непрерывное**, кусочно-линейное по опорным
точкам, чтобы прогноз мог быть дробным («3.4») и рост был виден до перехода через
границу балла:

| `score` | Оценка |
|---|---|
| ≤ 0.30 | 2.0 |
| 0.45 | 3.0 |
| 0.60 | 4.0 |
| ≥ 0.80 | 5.0 |

Между опорными точками — линейная интерполяция. Целевой порог поступления
(«сдать на 4») соответствует `score ≥ 0.60`.

Показывается **с полосой погрешности** («Русский: 3.4 ± 0.5»). Полоса выводится
из `confidence` по темам: чем больше суммарный вес непроверенных тем, тем шире.
Полоса широкая,
пока много непроверенных тем, и сужается по мере накопления данных. Подписано как
прогноз, а не измерение: родителям, принимающим решение о школе, нельзя показывать
уверенное число там, где уверенности нет.

**Калибровка — пробный экзамен раз в неделю**: полный набор заданий в формате
теста по всем темам, без подсказок. Сверяет прогноз с фактом и подтягивает
коэффициенты. Дополнительная польза — тренировка самого формата экзамена.

## Игровой слой

- **XP** за задание; больше за сложное и за решённое без подсказки.
- **Стрик по дням** — первая метрика на главном экране.
- **Босс темы**: при `mastery > 0.75` напарник предлагает бой — 5 заданий подряд
  без подсказок. Успех закрывает тему, и она гаснет на карте.
- **Обратный отсчёт** до экзамена рядом с полосой готовности по каждому предмету.

Сознательно **отсутствуют**: таймеры на задание, «жизни», штрафы за ошибку.
У ученика с тройками-четвёрками достаточно тревоги вокруг учёбы; дополнительное
давление ведёт к тому, что приложение закрывается на третий день.

## Родительский дашборд

Страница `/parents`, только чтение, без настроек (чтобы не превратилась в пульт
управления).

- прогноз по трём предметам с полосой погрешности и трендом за неделю;
- **честное время**: план 90 минут / факт 35 минут, без приукрашивания;
- топ-5 проблемных тем обычными словами («путает слитное и раздельное написание
  НЕ», не `russian.ne_spelling`);
- лента забегов;
- флаги: «три дня без занятий», «прогноз по русскому не растёт пятый день»,
  «математика вышла на 4.1, можно снизить нагрузку».

**Принципиальное ограничение: ученик видит ровно тот же дашборд и знает о нём.**
Никакой слежки за спиной. Приложение, ставшее инструментом контроля, перестаёт
быть его приложением, и мотивация умирает вместе с этим.

## Профиль ученика

Редактируемый в настройках: имя, интересы (игры, стримеры, увлечения), дата
экзамена, имя напарника. Интересы подставляются в промпт генерации и меняются в
любой момент без перезапуска.

## Синтез речи

**Диктант по русскому языку** — штатная функция: диктанты регулярно встречаются на
вступительных. Текст генерируется через codex, озвучивается ElevenLabs
(`ELEVENLABS_API_KEY` в окружении), аудио кэшируется на диск и переиспользуется.

**Аудирование по английскому** — задел на будущее, вне объёма MVP: на вступительном
в 7 класс обычно отсутствует.

## Технический стек

- **Бэкенд**: Node 26, TypeScript (ESM), Fastify
- **База**: SQLite через `better-sqlite3` (синхронный API, один пользователь)
- **Фронтенд**: React 19, Vite, Tailwind
- **Тесты**: Vitest, по TDD
- **Авторизация**: отсутствует — домашняя сеть, ученик и родители видят одно и то же

Тестами по TDD покрываются места, где ошибка тихая и дорогая: нормализатор
ответов, модель знаний, планировщик, парсинг вывода codex.

| `topic_state` | mastery, confidence, число попыток, last_seen, next_review |
| `task_bank` | сгенерированные и провалидированные задания |
| `attempts` | попытки: ответ, верность, подсказка, длительность |
| `runs` | забеги: предмет, тема, время, результат |
| `disputes` | спорные случаи из кнопки «я всё-таки прав» |
| `forecast_snapshots` | история прогноза для тренда |

На третий день ученик садится за рабочее приложение; дальше оно улучшается вокруг
него, а не он ждёт готовности.

**Уточнение по итогам реализации:** `server/forecast.ts` перенесён с дня 4 на
день 1. Это чистая функция без интерфейса, и она покрывается тестами вместе с
остальным ядром — на дне 4 остаётся только отображение прогноза. Реализовано в
[`docs/plans/20260807-edukator-core.md`](../../plans/20260807-edukator-core.md),
задача 9.

## Что сознательно не делается

- Аудирование по английскому — вне объёма MVP.
- Сюжетная игра с картой мира — неделя разработки, не двигающая оценку.
- Полная адаптивная диагностика — два часа из сорока и демотивация на старте.
- Авторизация и деплой в облако — приложение живёт в домашней сети.
- Таймеры, «жизни», штрафы — вредят мотивации целевого ученика.
