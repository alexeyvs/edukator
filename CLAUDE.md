# CLAUDE.md

Приложение для подготовки 13-летнего ученика к вступительным тестам в 7 класс за
40 часов. Спека: `docs/superpowers/specs/2026-08-07-edukator-design.md`,
многоарендность — `docs/plans/20260819-edukator-multi-tenancy.md` (отдельной
спеки у неё нет: замысел, калибровка и расхождения лежат в разделах «Overview»,
«Technical Details» и «Где реализация разошлась с замыслом» самого плана),
админка оператора — `docs/superpowers/specs/2026-08-21-edukator-admin-design.md`
и план `docs/plans/20260821-edukator-admin.md`,
планы этапов — `docs/plans/`.

## Команды

```sh
npm test                          # vitest, всё из tests/**/*.test.ts
npx vitest run tests/mastery.test.ts   # один файл
npm run coverage                  # пороги 80% пофайлово на ядре, занятии, маршрутах, генерации, многоарендности, админке (server/admin, server/routes/admin, server/log.ts, web/src/admin) и каркасе
npm run typecheck                 # отдельный tsc для server/scripts и web
npm run lint                      # eslint
npm run build:web                 # Vite production build в web/dist
npm run test:e2e                  # Playwright: вход, семья, агентский токен, забег, спор, триаж, босс, разбор, /parents, оператор
npm run dev                       # tsx watch на :3000 + Vite на :5173
npm start                         # сервер и собранная статика на :3000
npm run family:setup              # отдельное Python-окружение контроллера Family Safety
npm run family:login              # первичная авторизация родительского аккаунта
npm run family:test               # pytest контроллера; `npm test` его не видит
npm run start:family              # сервер и Family Safety controller одним запуском
npm run extract-toc               # оглавление учебника из PDF (OCR через swift + Vision)
npm run build-curriculum          # карта тем по извлечённому оглавлению, через codex
npm run parent -- create|invite|password|pin|disable --email <адрес>  # родители в control.db
npm run admin -- create|password|disable --email <адрес>  # операторы админки; приглашений по ссылке у них нет
npm run adopt -- --email <адрес> --name <имя>   # однопользовательская база → первый ребёнок
npm run backup -- --out <каталог> # копия каталога данных через VACUUM INTO
npm run prefetch -- --child <id>|--all  # ручной прогрев/экспорт банка; аргумент обязателен
./deploy.sh                       # проверка и атомарный деплой чистого HEAD на edukator.ru
```

Перед коммитом обязаны быть чистыми все пять: `test`, `coverage`, `typecheck`,
`lint`, `build:web`. Для изменений UI, HTTP-контрактов и `buildServer` обязателен
также `test:e2e`, а для изменений в `controller/` — `family:test`.

## Структура

- `server/*.ts` — чистая логика и доступ к базе, без CLI. Ядро — `normalize`,
  `mastery`, `scheduler`, `forecast`.
- `scripts/*.ts` — точки входа CLI. Могут импортировать из `server/`,
  **обратное направление запрещено**.
- **Баз две породы.** `control.db` знает, кто кем владеет и кто сейчас вошёл;
  детская база знает, что происходит на занятии. Ни `mastery`, ни `scheduler`,
  ни `run`, ни `daily-gate`, ни `parents` про `control.db` не знают и его
  соединения не получают: доменный модуль, которому понадобился арендатор, —
  признак, что граница проведена не там. Единственное исключение —
  `children.last_activity_at`: без него список активных детей узнаётся только
  открытием всех баз подряд, что противоречит ленивому реестру.
- `server/control-db.ts` — управляющая база: своя `CONTROL_SCHEMA_VERSION`
  (сейчас **2**), своя `migrateControl`, свой `validateControlSchema`.
  Одиннадцать таблиц: `parents`,
  `parent_invites`, `parent_sessions`, `children`, `child_devices`,
  `codex_quota`, `login_attempts` и четыре админских — `admins`,
  `admin_sessions`, `admin_impersonations`, `admin_audit`. `login_attempts`
  переехала на `kind IN ('password','pin','admin')`, и `kind` входит в ключ
  `(scope, kind, key)`: счётчик перебора у оператора **отдельный** от семейного.
  Общий означал бы, что перебор чужого родительского пароля запирает вход
  оператору, то есть служит способом ослепить его перед следующим шагом. **Путей детских баз в ней нет**: путь
  вычисляется из непрозрачного `children.id` (`CHILD_ID_PATTERN`), канонизируется
  и проверяется на принадлежность `children/`. Токены хранятся только
  SHA-256-отпечатком от 256-битного `randomBytes`, погашение приглашения и
  резерв квоты идут `UPDATE ... WHERE` внутри `transaction(...).immediate()`.
- `server/secrets.ts` — `scrypt` с индивидуальной солью и строкой
  `scrypt$N$r$p$соль$хеш`; длина пароля ограничивается **до** KDF, иначе длинный
  пароль становится способом занять процессор. `server/parent-pin.ts` — формат
  6–12 цифр, серверный pepper из `EDUKATOR_PIN_PEPPER` (в базе его нет) и
  сравнение постоянного времени; без pepper проверка PIN отказывает, а не
  проходит.
- `server/auth.ts` — четыре вида предъявителя и жёсткий порядок разрешения:
  разобрать предъявителя → **одной выборкой** проверить принадлежность ребёнка →
  и только затем открыть базу. Обратный порядок опасен не соединением, а тем, что
  `runId` и `itemId` нумеруются в каждой базе с нуля: ошибка выбора базы кончается
  не отказом, а успешной операцией над чужой строкой с тем же номером. «Не ваш
  ребёнок» и «нет такого ребёнка» — один ответ `no-child`. Заход оператора
  (`resolveImpersonatedBearer`) проверяется **первой** веткой на пути к чужой
  базе: собственные cookie оператора живы на его же машине, и без приоритета
  он видел бы свою семью там, где просил чужую. Админские маршруты этой ветки
  не касаются вовсе (см. `createAdminContext`).
- `server/tenant-opener.ts` — единственное место, где решается, какое соединение
  получит запрос: `TenantOpener.open(childId, { kind, impersonated })`. Ученик за
  экраном получает пишущую аренду и будит прогрев; оператор под заходом —
  соединение с `PRAGMA query_only = ON` и не будит ничего. Признак предъявителя
  в сигнатуре обязателен намеренно: забытый на новой точке вызова, он молча
  вернул бы обе отключённые вещи. Отдельным модулем, а не замыканием
  `buildServer`: второй замок имперсонации обязан проверяться без сервера.
- `server/tenant-registry.ts` — реестр детских баз: `open(childId)` с кешем,
  замком на первое открытие, миграцией, посевом и своими `DisputeCoordinator`
  и `IntegrityCoordinator`. Оба координатора пишут только в базу своей аренды;
  при закрытии реестр дожидается обоих.
  Вытеснения нет намеренно: потолок открытых баз (`DEFAULT_MAX_OPEN_TENANTS = 32`,
  переопределяется только опцией `buildServer({ maxOpenTenants })` — переменной
  окружения для него нет) отказывает новому арендатору и **не** трогает уже
  открытых, иначе закрытие уводило бы базу из-под идущей транзакции.
- `server/data-dir.ts` — каталог данных (`EDUKATOR_DATA_DIR`): `control.db` рядом
  с `children/<id>.db`, создание каталога и протокол заведения базы ребёнка
  (`provisioning` → временный файл → `fsync` → `rename` → `ready`). Прежней
  глобальной точки `EDUKATOR_DB` нет: баз столько, сколько детей.
- `server/backup.ts` — снимок одной базы через `VACUUM INTO` с `fsync` и
  `quick_check`; `scripts/backup.ts` обходит им весь каталог данных. Источник
  открывается голым `better-sqlite3` в `readonly` — и управляющая база, и детская.
  Через `openControlDatabase` бэкап включил бы WAL и прогнал бы `migrateControl`,
  то есть снимок, снятый перед обновлением, оказался бы уже обновлённым; а обычное
  соединение, закрываясь последним, слило бы `-wal` в основной файл и убрало
  спутники — снятие копии меняло бы оригинал ровно в том состоянии (оставшийся
  после аварии журнал), ради которого копию и снимают, а `npm run adopt` при этом
  обещает, что оригинал не тронут. Отказ
  одного ребёнка не отменяет копию остальных — он попадает в `failed[]` и в код
  возврата.
- `server/client-address.ts` — ключ счётчиков перебора: адрес сокета, а при
  доверенном прокси — разбор `X-Forwarded-For` справа налево. Длинная цепочка
  режется **с правого края** (`slice(-MAX_FORWARDED_HOPS)`): слева лежит то, что
  дописал сам клиент, и срез хвоста оставил бы в окне только подложенное.
- `server/data-lock.ts` — файловый замок каталога данных. Он не про файлы, а про
  бюджет codex: предел одновременных вызовов процессный, и второй процесс на том
  же каталоге заводит вторую пару слотов. Брошенный после аварии замок снимается
  только вручную после проверки PID: автоматический перехват не умеет атомарно
  отличить старый файл от нового живого замка конкурента.
- `server/dispute-coordinator.ts` — состояние разбора споров **на арендатора**:
  очередь, таймеры повтора и восстановление незакрытых споров при открытии
  **каждой** базы. В замыкании `registerSessionRoutes` его больше нет.
- `server/routes/tenant-context.ts` — единственное место, где маршрут получает
  `db`: `ROUTE_ACCESS` (`child`, `gate`, `dashboard`, `admin`) и перевод
  `AuthError` в код ответа. Админские маршруты аренды не получают вовсе и идут
  через `createAdminContext`: он смотрит только `__Host-edu_admin` и об
  имперсонации не знает — иначе приоритет захода вернул бы на `/api/admin/*`
  предъявителя чужой семьи, и админка отказывала бы ровно тогда, когда оператор
  хочет из захода выйти. `server/routes/token-privacy.ts` — замена сегмента
  токена на `<token>`: `redactTokenUrl` для адреса целиком, `redactTokenText`
  для токена внутри фразы (журнал пишет «не удалось погасить /join/<токен>:
  причина», и на таком тексте разбор адреса не срабатывает вовсе).
- `/api/health` не авторизован, а оба его аварийных состояния (сломанная
  управляющая база, отвязанный файл ребёнка) держатся до перезапуска, поэтому в
  журнал уходит **переход** состояния, а не факт опроса. Запись на каждый опрос
  — не диагностика, а её уничтожение: весь ретеншен журнала равен
  `LOG_MAX_BYTES × LOG_KEEP_FILES`, и монитор с минутным интервалом вытеснил бы
  из него ровно ту запись, которая называет причину.
- `server/log.ts` — хранилище аварий: `logFailure({ event, message, detail?,
  childId?, route?, status? })` в `<каталог данных>/logs/app.jsonl`, ротация по
  `LOG_MAX_BYTES = 8 МБ` при `LOG_KEEP_FILES = 4` — произведение и есть весь
  ретеншен, удаления по времени нет. `event` — **закрытое** объединение типов
  (`LOG_EVENTS`): свободная строка означала бы, что опечатка на новой точке
  вызова заводит невидимую фильтру категорию. У каждого имени списка обязано
  быть место вызова, и это проверяется тестом: событие, которое никто не пишет,
  — вариант фильтра, всегда дающий пустую ленту, а пустая лента читается как
  «аварий такого рода не было». Выбрав `backup-failed`, оператор получал бы
  утверждение о целости копий, ни на чём не основанное. Поэтому `backup-failed`
  и `prefetch-failed` пишут сами скрипты (их зовут из cron, и код возврата не
  видит никто), `codex-run-failed` — диспетчер на обходе, где codex **запустился**
  и не дал ничего (просроченная авторизация, кончившийся баланс: снаружи это
  выглядит работающей моделью и в `codex-unavailable` не попадает), а
  `login-lockout` — общий `server/routes/login-lockout.ts` на всех четырёх
  дверях. Он пишет **переход** в запрет, а не каждый отказ: `checkLoginGate`
  отказывает раньше счётчика, так что `locked` возвращает ровно та попытка,
  которая предел и перешагнула, — а строка на каждый отказ дала бы подбирающему
  способ выдавить из хвоста журнала всё остальное. Тел запросов и содержимого
  ответов ребёнка в журнале нет. Отказ самой записи уходит в stderr и запрос не
  роняет: журнал заводился ради аварий, а не ради новых. Каталог данных знает не
  всякий модуль, поэтому `registerErrorHandler` и `WarmupDispatcher` берут
  `FailureLog` (`failureLogFor(dir)`) **обязательным** аргументом — как и
  маршруты входа (`registerAuthRoutes`, `registerAdminAuthRoutes`,
  `registerParentsRoutes`), которым он нужен под `login-lockout`. Забытая
  передача обязана падать на сборке, а не терять аварию. Чтение — только
  **хвост** (`LOG_TAIL_BYTES = 512 КБ` текущего файла, при нужде предыдущий),
  первая оборванная строка отбрасывается, битые — поштучно, страница
  `ADMIN_LOG_PAGE = 200`, курсор `before` — `<отметка>#<сколько записей этой
  отметки отдано>` (аварии приходят пачкой, и плоская отметка теряла бы соседей
  по границе или повторяла их вечно).
- `server/admin/` — три слоя статистики оператора и обе половины захода.
  Выведенный ребёнок (`retired_at`) считается в них ровно один раз —
  выведенным: `retireChild` трогает только `retired_at`, и без оговорки в
  запросе четыре числа перестали бы разбивать `total`, а клиент по одному
  `status === 'ready'` предлагал бы заход, который `isChildServiceable`
  отвергает.
  `overview.ts` — слой 1, только `control.db` и `statSync` по вычисленному пути:
  главный экран обязан открываться ровно тогда, когда с детскими базами беда, и
  ни одной из них не открывает. `stats.ts` — слой 2, обход всех детских баз с
  кешем `ADMIN_STATS_TTL_MS = 5 минут` и отметкой времени в ответе; пересчёт —
  явным `refresh`. `child-detail.ts` — слой 3, одна названная база, без кеша: по
  жалобе смотрят состояние **сейчас**. `child-readonly.ts` — соединение отчётов:
  голый `better-sqlite3` в `readonly` с `fileMustExist`, без миграции и мимо
  реестра, живёт один запрос (`openDatabase` включил бы WAL и мигрировал бы
  чужую базу, а реестр отдал бы отчёту потолок в 32 аренды). Содержания не
  читает ни один слой: ни текстов ответов, ни формулировок споров, ни теории —
  прочитать написанное ребёнком можно только заходом, а он попадает в
  `admin_audit`. `impersonation-tenants.ts` — второй замок (`query_only` на
  своём соединении **и** отказывающие `disputes`/`integrity` вместо
  координаторов реестра: те носят пишущее соединение),
  `impersonation-refusals.ts` — процессный счётчик отказов
  первого замка, который доживает до записи `impersonation-end`,
  `impersonation-finish.ts` — общая запись конца захода: её пишут и явный выход
  из семьи, и выход из самой админки.
- `server/routes/admin/{auth,overview,stats,children,logs,impersonate,audit}.ts` —
  тонкие адаптеры админки. `server/routes/auth.ts` они не трогают: вход
  оператора с входом семьи не имеет общего ничего, а место второго фактора
  оставлено ровно между сверкой пароля и выдачей cookie.
- `server/codex/quota.ts` — суточная квота вызовов, надетая на сам `CodexRunner`.
- `server/codex/dispatcher.ts` — один фоновый цикл на процесс, обходящий детей.
- Отказ одного ребёнка не отменяет работу над остальными ни в одном обходе
  каталога: и `backupDataDir`, и `prefetchChildren` ловят его по ребёнку,
  складывают в `failed[]` и доносят кодом возврата. Вылет наружу оставил бы
  каталог полукопией, а семью — с холодной очередью у всех, кто стоял в списке
  дальше.
- `scripts/parent.ts`, `scripts/admin.ts`, `scripts/adopt-single-user.ts`,
  `scripts/backup.ts` —
  родители, операторы, разовый перенос однопользовательской базы и копия
  каталога данных. У оператора нет ни самостоятельной регистрации, ни
  приглашения по ссылке: он видит чужие семьи, и завести его можно только с
  самой машины, где лежит `control.db`. Пароль оба скрипта читают со stdin
  общим `createSecretReader`, а разбор аргументов и `--data-dir` держит общий
  `scripts/account-args.ts`.
  `prefetch` и `adopt` берут замок каталога данных, `backup` — нет: копию
  снимают при живом сервере, а замок стоит на бюджете codex, которого снятие
  копии не тратит. Детскую базу ни один из них не заводит: `openDatabase` там
  идёт с `fileMustExist: true`, иначе отсутствующий файл превращался бы в пустую
  базу, наполнялся и отчитывался успехом поверх потерянного прогресса.
- `deploy.sh` — локальная половина деплоя: гейты, `build:web`, упаковка чистого
  `HEAD`, отправка на хост. `scripts/deploy-release.sh` — серверная половина:
  снимок баз, подмена `app`, health и автоматический откат. Обе — shell, а не
  `scripts/*.ts`: они запускаются там, где приложения ещё (или уже) нет.
  Серверная половина обязана проверять `EDUKATOR_DATA_DIR` из файла окружения:
  без переменной приложение берёт умолчание `<корень проекта>/data`, то есть
  каталог **внутри** `app`, и деплой унёс бы живые базы вместе с прежней
  версией, поднялся бы на пустой `control.db`, прошёл health зелёным и стёр бы
  единственную копию по сроку хранения релизов.
- `scripts/toc.ts` намеренно без ввода-вывода: эвристика поиска оглавления
  тестируется на синтетическом тексте, без PDF.
- `server/run-child.ts` — единственная точка запуска внешних процессов: закрывает
  stdin, ограничивает срок и общий вывод, завершает всю группу процесса. Она же
  снимает живые группы, если родитель уходит раньше них: `detached` выводит
  потомка из группы терминала, так что Ctrl-C по `npm run prefetch` до него не
  доходит, а срок, который снял бы его, умирает вместе с родителем. Смерть по
  сигналу процессу досылается руками — но только там, где сигнал до нас никто не
  слушал: у сервера на нём висит `closeOnSignals`, и убийство из-под него
  оборвало бы закрытие базы.
- `server/session.ts` — логика занятия (выдача, приём ответа, разбор спора),
  `server/routes/session.ts` — только разбор запроса и коды ответов. Логику в
  маршрут не переносить: занятие проверяется без HTTP.
- `server/run.ts` — жизненный цикл строки `runs`: старт/возобновление, закрытие,
  прогресс и итог. Он собирает итог по истории `attempts`, пишет снимок прогноза
  и не выбирает отдельные задания. Незавершённый забег и забег с открытым
  спором закрывать нельзя.
- `server/triage.ts` — только политика следующего диагностического задания:
  новая тема, ступень сложности и досрочное завершение. Принадлежность забега,
  его `kind` и закрытость проверяет `server/routes/triage.ts`; запись ответа
  остаётся обычным путём `session`.
- `server/xp.ts` — единственная формула XP. `session` начисляет XP за ответ,
  `run` суммирует его по попыткам; копию формулы в маршрутах или клиенте не
  заводить.
- `server/streak.ts` считает серии только по завершённым обычным забегам и
  календарным дням `Europe/Moscow`; триаж и босс в серию не входят.
- `server/boss.ts` — доменные переходы боя и постоянное закрытие темы;
  `server/boss-loss.ts` — атомарное поражение и заказ замены;
  `server/boss-prep.ts` — claim, генерация вне транзакции и атомарный резерв
  полного набора. Порог доступности строгий (`mastery > BOSS_MASTERY`), победа
  требует ровно `BOSS_TARGET` верных ответов.
- `server/learning.ts` — атомарный жизненный цикл персонального материала:
  claim/recovery, открытие, последовательные lesson-run до зачёта, завершение и
  retirement с возвратом неоткрытых заданий в обычный банк. Повтор использует
  те же пять вопросов, но его ответы не влияют на XP, mastery и учебную статистику.
- `server/subject-calibration.ts` — единое правило калибровки предмета: завершённый
  триаж либо покрытие до 12 экзаменационных тем обычными завершёнными забегами.
- `server/learning-prep.ts` — выбор приоритетных пробелов, фоновая генерация,
  проверка и атомарная публикация полного материала с тестом.
- `server/routes/learning.ts` — тонкие HTTP-адаптеры чтения, открытия, старта и
  завершения персонального материала.
- `server/codex/learning-material*.ts` — структурированная генерация теории и
  независимая проверка её безопасности и содержания.
- `server/parents.ts` одним чтением строит read-only семидневную сводку:
  прогнозы, активное время из `attempts.duration_ms`, пробелы, ленту и флаги.
  Округлять миллисекунды можно только в read model; дневные значения и итог
  должны происходить из одной выборки.
- `server/integrity.ts`, `server/codex/integrity.ts` и
  `server/routes/integrity.ts` — обязательная проверка осмысленности обычного и
  lesson-забега до зачёта. Состояние живёт в `integrity_reviews` и
  `integrity_items`; детские маршруты повторяют отмеченный вопрос, а родительские
  detail/approve всегда называют `:childId` и используют координатор этой аренды.
- `server/daily-gate.ts` — единственный расчёт дневного доступа: `automaticUnlocked`
  требует три завершённых обычных забега и зачёт первого обязательного
  персонального разбора, активный `blocked | unlocked` override действует до
  следующей московской полуночи, а `unlocked` содержит эффективный итог. Материал
  выбирается по `ready_at`, затем `id`, но публикация после третьего забега
  переносится на следующие московские сутки. Триаж, boss и lesson не считаются;
  автоматически `retired` кандидат остаётся выбранным с `required=false` до
  конца назначенных суток, чтобы следующий материал не подменил отменённое обязательство;
  `/api/run/plan` и `/api/gate/status` обязаны использовать один результат.
- `controller/` — отдельный Python-контроллер закрытого мобильного API Microsoft
  Family Safety. Он знает только read-only `gate/status`, ходит туда агентским
  токеном в заголовке, не читает SQLite и не хранит ни refresh token, ни этот
  токен в репозитории: оба лежат в конфигурации с правами `0600`. Живой
  Microsoft API не вызывается тестами. Четыре правила его похода за `gate/status`:
  открыватель собирается с `ProxyHandler({})` и запретом переходов — иначе
  `Authorization: Bearer <агентский токен>` уехал бы настроенному `http_proxy`
  открытым текстом; тело режется `MAX_GATE_BODY`; общий срок
  `timeout * GATE_DEADLINE_FACTOR` держится **трижды** — снаружи `asyncio.wait_for`,
  внутри чтения тела и сторожем соединения на чтении статуса с заголовками
  (`_DeadlineConnection`), потому что брошенный `to_thread` не прерывается, а
  сокетный таймаут отмеряет отдельную операцию: бесконечная череда `100 Continue`
  иначе держала бы поток на сокете вечно. Разъехавшиеся числа дают либо вечный
  поток, либо ранний отказ. Чтение
  предыдущего состояния и настроек опроса намеренно нестрогое (`load_config`
  строгий): строгость здесь отказывала бы ровно на конфигурации прошлой версии,
  то есть при обновлении.
- `server/routes/{run,triage,integrity,profile,boss,learning,parents,gate,auth,family}.ts` —
  тонкие HTTP-адаптеры над доменными модулями и `writeProfile`; бизнес-логику
  держать вне маршрутов. Родительские маршруты называют ребёнка в пути
  (`/api/parents/:childId`, включая detail/approve), детские — нет: ребёнок один
  на сессию. PIN на изменяющем родительском маршруте нужен только предъявителю
  детского устройства; родительская cookie уже подтверждена паролем.
  `family.ts` — единственный из них, кто аренды не получает вовсе и разрешает
  запрос сам (`requireParent`): поэтому первый замок имперсонации там выписан
  руками, а общая матрица `ROUTE_ACCESS` эти маршруты не проверяет.
- `server/codex/concurrency.ts` — процессные семафоры вызовов codex:
  два общих места для обычного прогрева, подготовки боссов, персональных
  материалов и integrity-review, отдельное место только для споров. Для boss-,
  learning- или integrity-конвейера
  нельзя заводить собственный бюджет Codex: иначе суммарная фоновая конкуренция
  превысит предел. Фоновая работа не должна мочь занять слот спора. Семафоры
  остаются **процессными** и с несколькими детьми: честность между ними даёт
  диспетчер и суточная квота, а не второй бюджет.
- `server/scheduler.ts` — единственный источник состава активных тем. И выдача
  занятия, и воркер используют `activeTopics`: сначала все незакрытые обычные
  забеги (самый свежий первым), затем план. Перенесённые забеги исключаются из
  новых рекомендаций, но остаются в активных темах. Свою копию этого выбора в
  `session` или `worker` не заводить.
- `server/codex/` — всё, что связано с моделью: `client.ts` (общий клиент —
  аргументы, запуск, схема для `--output-schema`, разбор ответа, карта ролей и
  выбор модели по роли; ничего предметного, сборка карты тем и генерация заданий
  зовут один и тот же код),
  `prompt.ts` (все промпты, `TASK_BATCH_SIZE`, `RECENT_LIMIT`, а также
  `MAX_ANSWER_LENGTH` — межмодульный инвариант: тот же предел ставит на тело
  запроса `server/routes/session.ts`, и разъезд дал бы вердикт спора по не тому
  тексту, который засчитается), `task-schema.ts`
  (инварианты сверх схемы; через него проходит и ответ модели, и посевной файл),
  `generate.ts`, `validate.ts`, `dispute.ts`, `bank.ts`, `worker.ts`,
  `dispatcher.ts`, `quota.ts`, `seed-bank.ts`.
- `server/codex/worker.ts` греет **одну** базу и об остальных детях не знает:
  `runWarmupCycle` получает целевой запас, предел батчей и признак «фаза
  излишков», в которой готовятся босс и персональный материал. Кого обходить и в
  каком порядке, решает `server/codex/dispatcher.ts`: сначала все, кому не
  хватает до `REFILL_BELOW`, и ученик за экраном в этой очереди первый; только
  когда всем есть на чём заниматься, второй заход добивает запас до
  `QUEUE_TARGET`. Указатель обхода переживает цикл, иначе последний ребёнок
  доходил бы до генерации только в редких обходах. `wake(childId)` будит цикл
  из маршрута; отступ по `CodexUnavailableError` остаётся процессным.
- `server/codex/bank.ts` хранит единственный внутренний примитив подготовки и
  вставки задания: текст, отпечаток, дедупликацию и JSON-поля. И обычный
  `storeTasks`, и резерв босса обязаны использовать его; отдельная реализация
  записи для `boss_tasks` быстро разойдётся с валидацией обычного банка.
- `tests/` — один файл на модуль, имена совпадают.
- `web/` — React 19 + Vite + Tailwind. `web/src/*-api.ts` держат HTTP-контракты,
  экраны не должны собирать `fetch` каждый по-своему. `web/dist` — результат
  `build:web`, а не исходник для ручной правки.
  Обычный забег и триаж отображают условие общим `TaskPrompt`: материал отделён
  от инструкции, а display-LaTeX рендерится KaTeX с `trust: false`, лимитами
  размера и экранированным исходником при ошибке разбора.
  Какое состояние рисовать, решает чистая `web/src/app-route.ts` (адрес плюс
  ответ `/api/auth/me`), а `App.tsx` остаётся сборкой: страница по ссылке
  (`/invite/:token`, `/join/:token`), админка (`/admin`, `/admin/child/:childId`),
  никто не вошёл (вход родителя), родитель (семья и сводки детей), ребёнок
  (обычное приложение). На админском адресе `me` не спрашивается вовсе: под
  заходом он назвал бы предъявителя чужой семьи, а не оператора. 401
  разбирается в `web/src/http.ts` отдельно от «не удалось загрузить», иначе
  каждый экран вместо «войдите» показал бы поломку; `read-only` разбирается там
  же отдельным кодом — работающий замок иначе выглядел бы поломкой. Токен из
  адресной строки убирается `history.replaceState` сразу после загрузки.
- `web/src/admin/` — экраны оператора (`AdminApp` — корень, `AdminLoginScreen`,
  `AdminHomeScreen`, `AdminStatsScreen`, `AdminChildScreen`, `AdminLogsScreen`,
  `ImpersonationBanner`), контракт — один `web/src/admin-api.ts`. Вход оператора
  отдельным экраном от `LoginScreen` намеренно: публичный корень не должен
  предлагать форму входа в админку. Лента аварий — состояние внутри `AdminApp`,
  а не второй адрес: в `APP_PAGES` его нет, и ссылка ломалась бы 404 статики.
  Закрытый список событий журнала продублирован на клиенте
  (`ADMIN_LOG_EVENTS`) — импортировать `server/` клиенту нечем, а без списка у
  фильтра нет вариантов на пустом журнале; синхронность копии держит
  `tests/log.test.ts` сверкой с текстом `web/src/admin-api.ts`.
- `e2e/` — Playwright-сценарии с сервером, поднятым самим тестом через
  `buildServer` на временном **каталоге данных**. `npm start` здесь запрещён:
  через него нельзя подменить reviewer, воркер и защиту от настоящего codex.
  Сценарий начинается с заведения родителя и ребёнка прямо в `control.db` и
  погашения детской ссылки: cookie предъявителя — часть каждого пути.
- `content/curriculum/*.json` — истина по составу тем. `topic_state` в базе
  хранит только прогресс и приводится к карте через `syncTopicState`, который
  ничего не удаляет.
- `content/persona.md` — единственный источник тона напарника, читается до
  первого вызова codex; его отсутствие — ошибка настройки, а не умолчание.
- `content/seed-bank/*.json` — снимок банка для первого запуска и отката. Это
  такой же непроверенный текст, как ответ модели, и проходит тот же
  `parseTaskBatch`.
- `schemas/*.json` — схемы данных: `curriculum.json` (карта тем), `tasks.json`
  (батч заданий), `verdicts.json` (вердикты проверяющего), `dispute.json`
  (разбор спора), `learning-material.json` (безопасная теория) и
  `learning-verdict.json` (вердикт методиста). Рукописной копии в коде нет; вариант для codex получается из
  той же схемы вырезанием запрещённых ключевых слов (`codexOutputSchema`), а
  ограничения, которые оно снимает, проверяет разбор ответа.
- `server/json-schema.ts` — общая обвязка над Ajv: компиляция схемы из файла и
  текст ошибок. Настройка Ajv нигде больше не повторяется.
- `server/atomic-write.ts` — запись файлов, которые лежат в репозитории и служат
  единственным снимком состояния (карта тем, посевной банк, распознанное
  оглавление — самих PDF в репозитории нет): соседний временный
  файл, `fsync`, `rename`. Такой файл пишется только через `writeFileAtomic` —
  оборванная запись оставила бы вместо снимка битый JSON. Уборка в `catch`
  обёрнута своими `try`: отказ закрытия не имеет права заслонить причину.
- Схема **детской** базы версии 17 содержит пятнадцать таблиц: `profile`, `topic_state`, `task_bank`,
  `runs`, `attempts`, `disputes`, `forecast_snapshots`, `boss_batches` и
  `boss_tasks`, `learning_materials`, `learning_runs`, `learning_tasks`,
  `computer_access_override`, `integrity_reviews`, `integrity_items`. Последние
  две хранят состояние проверки занятия и решения по его ответам в пределах
  одной аренды. `computer_access_override` хранит не больше одной ручной команды
  `blocked | unlocked` до следующей московской полуночи. `topic_state.closed_at`
  закрывает тему постоянно;
  `task_bank.status = 'boss_reserved'` не виден обычной выдаче, а порядок боя
  задаётся только `boss_tasks.position`, не `task_bank.id` и не временем.
  Аналогично `lesson_reserved` не виден обычной выдаче, а порядок теста задаёт
  только `learning_tasks.position`. Retirement неоткрытого материала возвращает
  его задания в `valid`; открытый материал сохраняет набор для повторов до зачёта.
  `profile` остаётся строкой на базу — теперь это ровно то, чем он и задуман:
  профиль одного ученика. `computer_access_override` тоже остаётся здесь: это
  состояние ученика, а не учётной записи.

## Конвенции

**Язык.** Все комментарии, тексты ошибок и названия тестов — по-русски.
Комментарий объясняет *почему*, а не *что*: то, что видно из кода, не дублируется.

**Числа калибровки — константы с тестом на буквальное значение.** `ALPHA`,
`GAP_MASTERY`, `MAX_REVIEW_DAYS`, `SUBJECT_FLOOR` и прочие заданы спекой. Тесты,
которые строят ожидание из той же константы, её подмену не ловят, поэтому в
каждом модуле ядра и в воркере (`QUEUE_TARGET`, `REFILL_BELOW`,
`MAX_CODEX_CONCURRENCY`) есть отдельный тест «держит калибровочные константы
спеки» с числами вписанными руками. Меняете число — меняйте и спеку. То же
правило действует на многоарендность: `PARENT_INVITE_TTL_MS`,
`PARENT_SESSION_IDLE_MS`/`_MAX_MS`, `SESSION_TOUCH_MS`, `DEVICE_INVITE_TTL_MS`,
`CODEX_DAILY_QUOTA`, `LOGIN_*_FAILURE_LIMIT`, `LOGIN_LOCKOUT_MS`,
`MAX_FORWARDED_HOPS`, `ACTIVE_WINDOW_MS`/`AT_SCREEN_MS`, `DISPUTE_RETRY_MS`,
`MIN_PIN_PEPPER_LENGTH`, `MAX_CHILD_NAME_LENGTH`/`MAX_DEVICE_LABEL_LENGTH`, и на
админку: `MIN_ADMIN_PASSWORD_LENGTH`, `ADMIN_SESSION_IDLE_MS`/`_MAX_MS`,
`IMPERSONATION_TTL_MS`, `ADMIN_STATS_TTL_MS`, `LOG_MAX_BYTES`, `LOG_KEEP_FILES`,
`LOG_TAIL_BYTES`, `ADMIN_LOG_PAGE`, `ADMIN_AUDIT_PAGE`, `CHURN_SILENCE_DAYS`,
`WORST_TOPICS_LIMIT`/`WORST_TOPIC_MIN_ANSWERS`, `STUCK_PROVISIONING_MS`,
`OVERVIEW_WINDOW_DAYS`. Там,
где число прячется в вычислении (отступ повтора спора, пауза обхода), формула
вынесена отдельной функцией (`nextDisputeRetryDelay`, `backoffDelay`) — тесты
гоняют координатор с паузой в миллисекунду, и на ней постоянная задержка
неотличима от растущей.

**Предел пароля и формат PIN продублированы на клиенте.**
`web/src/InviteScreen.tsx` держит свой `MIN_PASSWORD_LENGTH = 10`, а
`web/src/pin-format.ts` — свой `/^\d{6,12}$/u`: импортировать из `server/`
клиент не может. Копия на клиенте ровно одна, и экраны («Семья», сводка
родителей) зовут `isParentPin`, а не пишут регулярку заново: второй экземпляр
разъезжается с первым молча. Это межмодульный инвариант того же рода, что
`MAX_ANSWER_LENGTH`, и обе копии обязаны иметь тест с числом, вписанным руками:
поднятый на сервере минимум оставил бы клиент, который молча принимает короткий
пароль и получает 400, а расширенный формат PIN — кнопку, отключённую по
устаревшему правилу. Тем же порядком продублированы `MIN_ADMIN_PASSWORD_LENGTH
= 16` в `web/src/admin/AdminLoginScreen.tsx` и закрытый список событий журнала
`ADMIN_LOG_EVENTS` в `web/src/admin-api.ts`.

**Готовность предпосылок — мягкая.** `prereqsReady` — только диагностический
признак «фундамент закрыт». Ранжирование использует `prereqsReadiness` с
`PREREQ_SOFT_FLOOR = 0.2`: возвращать затвор к нулю нельзя, иначе длинные цепочки
никогда не всплывают. Изменение формулы требует обновить раздел планировщика в
спеке и буквальный тест калибровочных констант.

**Отметки времени только в ISO (`toISOString`).** Сравнение по этим колонкам
строковое, `datetime('now')` даёт другой формат и всё ломает; умолчания схемы
используют `strftime('%Y-%m-%dT%H:%M:%fZ','now')`.

**Копия проверяется схемой только своей версии.** `backupDatabase` снимает
снимок **без** миграции, а детские базы мигрируются лениво, по первому обращению
реестра: сразу после обновления приложения база ребёнка, который с тех пор не
занимался, законно лежит со схемой прошлой версии. `scripts/backup.ts` поэтому
зовёт `validateSchema`/`validateControlSchema` только при совпадении
`user_version` с `SCHEMA_VERSION`/`CONTROL_SCHEMA_VERSION`; целость даёт
`quick_check`, который идёт всегда. Безусловная проверка давала бы код возврата
1 на исправной копии — то есть в цепочке `backup && rm -rf прошлая` убирала бы
последнюю целую из-за новой.

**Каждое изменение схемы — новая миграция.** Увеличить `SCHEMA_VERSION`,
добавить последовательный переход со всех поддерживаемых прошлых версий,
выполнить DDL/преобразование данных транзакционно и добавить тест обновления с
предыдущей версии. Правка одного `SCHEMA` не обновит базу с тем же
`user_version`; база новее приложения по-прежнему должна отвергаться. У
`control.db` **свои** `CONTROL_SCHEMA_VERSION` и `migrateControl`, не связанные
с версией детской базы: схемы живут своими циклами, и общий номер заставлял бы
поднимать версию при изменении в любой из двух. Правило целиком то же — версия,
последовательный переход, тест обновления с предыдущей.

**Предъявителей ровно четыре, и они не взаимозаменяемы.** `parent` — cookie
`__Host-edu_parent` с `SameSite=Strict`; `browser` — cookie `__Host-edu_child` с
`SameSite=Lax` (детская ссылка открывается переходом со стороны); `agent` —
токен устройства заголовком `Authorization: Bearer`, и ему доступен **ровно**
`GET /api/gate/status`; `admin` — cookie `__Host-edu_admin` с `SameSite=Strict`
и строкой матрицы `admin: ['admin']`. Агент — не детская сессия: он лежит файлом
на детской машине, и допуск его к обычным маршрутам означал бы, что этот файл
умеет сдавать ответы. Оператор — не родитель: аренды у его маршрутов нет вовсе,
и ни одна существующая строка матрицы значением `admin` не пополняется. Кто
именно пришёл, `allow` называет **обязательным** полем
(`ROUTE_ACCESS` в `server/routes/tenant-context.ts`): умолчания «родитель и
браузер» нет намеренно — забытый `allow` у нового маршрута открывал бы его молча
и вширь, а не падал бы на сборке. Матрица проверяется поимённо по **каждому**
зарегистрированному маршруту (`tests/tenant-context.test.ts` сверяет свою таблицу
с `onRoute`), потому что `allow` передаёт каждый обработчик отдельно, и подмена
его у одного модуля тремя URL не ловится.

Опрос агента активностью ребёнка **не** считается: `resolveChildDevice`
подновляет `children.last_activity_at` только у `browser`. Контроллер стучится в
`gate/status` раз в двадцать секунд, и считая это активностью, диспетчер держал
бы каждого оснащённого им ребёнка вечно «за экраном». По той же причине вид
предъявителя доезжает до `TenantOpener.open`, а будильник прогрева
(`dispatcher.wake`) дёргается только на `browser`: брошенный ребёнок в обход не
попадает, в `#served` его нет никогда, и опрос агента иначе срывал бы паузу
каждые двадцать секунд — получасовой отступ по недоступному codex не наступал бы
вовсе.

Пришли обе cookie — выигрывает детский принципал, **если** `__Host-edu_actor`
не назвал родителя явно. Cookie выбора роли сама по себе прав не даёт: обе
сессии проверяются серверно на каждом запросе, а роль `parent` в
`POST /api/auth/persona` подтверждается паролем — единственное место, где
родительскую сессию переспрашивают. `Secure` снимается
только явным `EDUKATOR_INSECURE_COOKIES=1` для локального http. `SameSite` за
защиту от CSRF не считается: все изменяющие запросы с cookie дополнительно
требуют совпадения `Origin` либо `Sec-Fetch-Site: same-origin`, и запрос без
обоих заголовков отклоняется. Изменяющим считается не метод, а то, что маршрут
делает: `GET /api/session/next` и `GET /api/triage/:id/next` списывают задание
из банка безвозвратно и потому идут с `mutating: true`, — детская cookie
`SameSite=Lax` уезжает и на переходе с чужой страницы. Новый `GET`, который
что-то списывает, обязан пометиться так же: иначе чужая страница жжёт банк
чужими руками.

**Заход оператора в чужую семью держат два независимых замка, и снимать
разрешается только оба сразу — то есть никогда.** Первый: `resolveTenant`
отказывает `read-only` (403) на `isMutating(method) || mutating === true`.
Второй: аренда выдаётся **своим** соединением с `PRAGMA query_only = ON`
(`server/admin/impersonation-tenants.ts`) — `mutating` у нового маршрута
забывается молча, и цена такой забывчивости не 500, а запись в чужую семью.
Подменяется при этом **вся** аренда, а не только `db`: `disputes` и `integrity`
реестра носят своё, пишущее соединение, и оставленные как есть они дают обычному
`GET` записать в чужую базу мимо обоих замков (`integrity.status` ставит
незакрытую проверку на разбор). Тест, остающийся зелёным после снятия любого
одного из них, не держит ничего: проверять их обязательно **по отдельности**.

Оба замка стоят на пути аренды, поэтому `/api/family/*` они не прикрывают:
аренды у этих маршрутов нет вовсе, а состав семьи, устройства и PIN лежат в
`control.db`, куда `query_only` не достаёт. Первый замок там выписан руками в
`requireParent` (`server/routes/family.ts`) и проверяется своим тестом: общая
матрица допуска эти маршруты не видит. Цена пропуска здесь выше обычной —
`POST /api/family/children/:id/devices` выдаёт **постоянный** токен устройства,
переживающий срок захода.

Заход живёт `IMPERSONATION_TTL_MS`,
ставится cookie `__Host-edu_impersonation` рядом с админской (вышедший оператор
обязан оказаться снова в админке, а не на экране входа), гасится сменой пароля,
отключением оператора, следующим заходом того же оператора и **выходом из самой
админки**: переживший выход заход выигрывает у собственных cookie оператора
первым же разбором предъявителя, а снять его нечем — явный выход требует
админской сессии, которую этот же выход и погасил. Под заходом не
подновляется `children.last_activity_at`, не дёргается `dispatcher.wake` и не
пишется ничего: оператор смотрит на семью, а не занимается за неё. Начало и
конец попадают в `admin_audit`, и в записи о конце стоит счётчик отказанных
попыток записи. Счётчик процессный и **истёкший** заход не закрывает — его
некому закрыть, `resolveImpersonation` просроченную строку уже не отдаёт, —
поэтому старт следующего захода счётчик сбрасывает: иначе попытки записи в
прошлой семье попали бы в запись о конце захода в следующей.

Пути, которыми оператор смотрит чужие экраны, обязаны читать **без** `BEGIN
IMMEDIATE`: `query_only` отменяет его целиком («attempt to write a readonly
database»), и чистое чтение под `.immediate()` превращает первый же экран в
пятисотку. Так уже ловились `runProgress` и `nextBossTask`; снимок чистому
чтению даёт отложенная транзакция.

**PIN спрашивается только с детского устройства.** Родительская сессия — уже
доказательство родительства, и второй раз его не спрашивают ни на одном
действии. PIN остаётся ровно для случая «родитель подошёл к машине ребёнка»:
детская сессия читает свою сводку без него, но ничего не меняет без него.
Пароль и PIN не принимаются флагами командной строки: аргументы видны в `ps` и
остаются в истории оболочки, поэтому `scripts/parent.ts` читает их со stdin.
Закрытый stdin — отказ, а не молчаливый успех: `readline.question` на EOF
обратный вызов не зовёт никогда, и без разбора события `close` процесс выходил бы
с кодом 0, не сменив ничего. Интерфейс `readline` при этом **один на запуск**
(`createSecretReader`): readline разбирает пришедший кусок на строки сразу, и
отдельный интерфейс на вопрос забирал бы из трубы обе строки, отдавал первую и
терял вторую — `printf 'пароль\nпароль\n' | npm run parent -- password`
отказывал бы «стандартный ввод закрыт», прочитав ровно половину ответа.
Управляющую базу заводит только `create`: остальные команды идут с
`fileMustExist`, иначе опечатка в `--data-dir` заводила бы пустую базу рядом и
отвечала «родителя нет в управляющей базе» — то есть называла виноватым адрес. Смена PIN, в отличие от смены пароля,
`credentials_changed_at` **не** трогает: PIN подтверждает родителя за детской
машиной, а не служит ключом от учётной записи. Сам `credentials_changed_at`
гасит четыре вещи: родительские сессии, погашенные токены детских устройств и
**ещё не погашенные** приглашения обоих видов (`INVITE_AFTER_CREDENTIALS`,
`DEVICE_INVITE_AFTER_CREDENTIALS`) — право поставить пароль по ссылке равно
полному входу, и утёкшая ссылка иначе пережила бы смену пароля, которую от неё и
советуют. Условие живёт одним текстом SQL и в проверке, и в погашающем
`UPDATE`: снимок между ними успел бы устареть.

**Единица суточной квоты — один `runCodexCli`, а не один `budget.run`.** За
одним слотом семафора прячется целый конвейер (батч — генератор и проверяющий,
персональный материал — теория, методист и вопросы), и счёт по слотам превратил
бы предел 60 в 120–360 настоящих запусков. Списываются и неудачные вызовы:
зацикливание на ошибках иначе обходит защиту, ради которой квота и заведена.
Квота стоит на расходе ребёнка за московские сутки, а не на способе запуска:
её списывает и `scripts/prefetch.ts`, поэтому ручной прогрев не оставляет
диспетчеру полный счётчик на те же сутки. Соединение с `control.db` живёт у
`prefetchChildren` до конца обхода именно поэтому.
Спор и проверка ответа квотой не трогаются: они идут по живому запросу ученика.
Исчерпанная квота выражается `CodexQuotaError`, наследником
`CodexUnavailableError`, — самому вызову она неотличима от недоступной модели.
Диспетчер, однако, переспрашивает квоту после цикла, отчитавшегося
недоступностью, и помечает ребёнка `skipped='quota'` вместо
`sweep.codexUnavailable`: `everySweepFailed` исключает таких детей целиком,
иначе один наигравшийся ребёнок уводил бы в получасовой отступ прогрев всей
семьи. По той же причине не состоявшийся заход (`skipped='error'` — испорченная
база, упавший на профиле цикл) решает за весь процесс только в одиночку: сосед с
полным банком попыток не даёт вовсе, и вердикт «всё упало» по одному чужому файлу
морозил бы прогрев всей семье, а ученику за экраном и снять паузу нечем — его
самого обход прошёл, и будильник его запроса её не отменяет.

**Read-modify-write и снимки — только в `transaction(...).immediate()`.** Под
WAL нельзя читать состояние вне транзакции и записывать позже: параллельная
фиксация потеряет патч либо даст `SQLITE_BUSY_SNAPSHOT`. Обновление модели и
истории попытки, а также пакет снимков прогноза, должны быть атомарны.

**Вызов модели никогда не идёт внутри транзакции.** Он занимает минуты и под WAL
всё это время держал бы запись — занятие вставало бы на каждом споре. Состояние
перечитывается заново уже под записью (`resolveDispute`): пока шёл вызов, его мог
закрыть параллельный разбор, и второй вердикт удвоил бы `accept[]`.

**Разделы промпта пишет только код.** Всё, что пришло не от нас — интересы из
профиля, прошлые формулировки, замечания неудачной попытки, условия чужой модели,
распознанное оглавление, `title` и `prompt_seed` из собранной по нему карты тем,
— не должно уметь открыть собственный раздел. Многострочное уходит блоком JSON
(`dataBlock`), однострочное — через `inlineField` со схлопыванием переводов строк
и обрезкой по длине. `JSON.stringify` одного экранирования не даёт: U+0085,
U+2028 и U+2029 он оставляет как есть, а модель читает их переводом строки,
поэтому `dataBlock` досылает их сам (четырьмя знаками: `\u85` — не escape JSON).
U+0085 вдобавок не входит в `\s`, поэтому в `inlineField` он выписан отдельно.
`dataBlock` **экспортируется** и служит единственной реализацией: сборка карты
тем (`scripts/build-curriculum.ts`) кладёт в промпт самый недоверенный текст
проекта и зовёт тот же код — своя копия правила разъехалась бы с общей молча.
Тесты режут промпт по всем этим знакам, а не по одному `\n`.

**Отказ занятия по состоянию — `SessionError` с кодом**, маршрут отображает его в
4xx. Всё остальное обязано остаться пятисоткой, и наружу из неё уходит только
общий текст: `setErrorHandler` в `buildServer` пишет подробности в stderr, потому
что в них локальные пути и содержимое базы, а сервер теперь смотрит наружу.

**Живая одноразовая ссылка не хоронится по не доехавшему запросу.** У
`readInvite`, `redeemInvite` и `claimDevice` отказ приезжает `HttpError` с кодом
(`web/src/http.ts`), и «попросите новую» пишется только на 404: погашение идёт
одним `UPDATE ... WHERE` и либо состоялось, либо не тронуло ничего. Обрыв сети и
503 неготового сервера дают экран с кнопкой «Повторить», а замок `claimed` в
`JoinScreen` на них сбрасывается — иначе отвергнутое обещание в нём осталось бы
окончательным ответом навсегда.

**Токен в логах не пишется.** Он виден в URL дважды — `/join/<token>` и
`/api/auth/parent/invite/<token>`, — поэтому сегмент токена заменяется на
`<token>` во всём, что уходит в stderr (`server/routes/token-privacy.ts`), а
страницы погашения отдаются с `Referrer-Policy: no-referrer` и
`Cache-Control: no-store`. Новый адрес с секретом в пути обязан попасть в тот же
список.

**Доверие к `X-Forwarded-For` — только от перечисленных адресов прокси**
(`EDUKATOR_TRUSTED_PROXIES`, по умолчанию loopback). Голое `trustProxy: true` —
не защита, а её отключение: клиент подставил бы новый заголовок на каждую
попытку и обошёл счётчик перебора. Счётчики неудач пароля и PIN живут в
`control.db`, а не в памяти процесса (перезапуск подбирающий вызвать умеет), и
работают fail-closed: недоступен счётчик — вход не пускаем.

**Что делать с недостающей строкой `topic_state`** зависит от места:
`readTopicState`/`recordAttempt` бросают (молчаливый ноль скрыл бы опечатку в
`id`), а планировщик и прогноз через `stateOf` считают её нулевым состоянием
(состав тем задаёт карта). Темы синхронизирует реестр арендаторов
(`TenantRegistry.#syncCurriculum` → `syncTopicState`) при **первом открытии**
базы ребёнка, до посева банка: строки заводятся лениво, вместе с самой базой, а
не при старте сервера — открытых баз на старте нет вовсе.

## TypeScript, ESM и что на этом ломается

`"type": "module"` плюс строгий tsconfig — четыре вещи, о которые спотыкается
новый код:

- **относительные импорты пишутся с `.js`** (`import { openDatabase } from
  './db.js'`), даже когда исходник — `.ts`;
- `verbatimModuleSyntax` требует `import type` для типов;
- `exactOptionalPropertyTypes` — необязательное поле добавляется спредом
  (`...(x === undefined ? {} : { x })`), а не присваиванием `undefined`;
- `noUncheckedIndexedAccess` — после индексации нужен `?? ''` или явная проверка.

## Тестирование

TDD обязателен для четырёх модулей ядра; для каркаса, схемы и скриптов
допустим обычный порядок. Тест, который проходит и после подмены проверяемого
кода, коврига не держит: сомневаетесь — испортите строку в `server/` и убедитесь,
что тест покраснел. Каждая задача плана обязана приносить тесты — и на
успешный путь, и на ошибочный.

Тесты работают на временных каталогах данных через `EDUKATOR_DATA_DIR` и
`mkdtempSync`: каталогом вместо файла, но так же одноразово. Тестам маршрутов и
`buildServer` нужен ещё и предъявитель — родитель и ребёнок заводятся прямо в
`control.db` помощником, а не через живой вход.
Заглушек три, и путать их нельзя. **Процесс и его коды возврата** — исполняемой
заглушкой: shell-скриптом в temp-каталоге, а не моком `spawn`, только так ловятся
закрытый stdin и коды возврата (оба вызова принимают `bin` именно ради этого).
**Политика** — подменяемым интерфейсом: `CodexRunner`, `TaskProducer`,
`DisputeReviewer`, `BackgroundRunner` дают проверить пороги очереди и логику
занятия, не запуская процессов. Настоящий codex не зовёт ни один тест.
**Внешние команды серверного деплоя** — каталогом-`PATH` с журналом вызовов:
`tests/deploy-release.test.ts` гоняет сам shell-скрипт, подставляя `systemctl`,
`runuser`, `npm`, `curl` и `chown` через `EDUKATOR_DEPLOY_*_BIN`, а
`EDUKATOR_DEPLOY_REQUIRE_ROOT=0` снимает требование root. Эти переменные
существуют ради теста и в боевом запуске не задаются — правя
`scripts/deploy-release.sh`, о них надо знать, иначе новый вызов внешней команды
окажется непроверяемым.

E2E поднимает `buildServer` внутри процесса. По умолчанию сценарии отключают
воркер; lesson- и boss-сценарии включают контролируемый воркер с подменёнными
`TaskProducer` и `LearningProducer`. `DisputeReviewer` также подменён, а первым
в `PATH` стоит исполняемый shim `codex`, который оставил бы маркер вызова.
После сценария отсутствие маркера проверяется явно.
Каждый сценарий получает свой временный каталог данных; статика у всех общая —
`npm run test:e2e` собирает `web/dist` один раз перед прогоном. Общий `npm start`
сделал бы сценарии зависимыми от локального профиля и очереди.

Общая установка тестов живёт в `tests/server-harness.ts` (родитель, ребёнок,
оператор и заголовки предъявителя в `control.db`) и
`tests/tenant-context-helper.ts`
(поддельное разрешение аренды для маршрутных тестов). Своя копия установки в
новом тесте разъедется с ними молча: тройка
`createAdmin`/`setAdminPassword`/`loginAdmin` уже была скопирована в пять
маршрутных тестов админки и сведена обратно к помощнику.

Контроллер доступа проверяется своим гейтом: `npm run family:test` (pytest в
окружении контроллера). `npm test` гоняет только Vitest и изменений в
`controller/` не увидит.

Новые внешние процессы запускаются через `runChild`, не напрямую через
`spawn`. Укажите положительный timeout; stdin остаётся `ignore`, stdout+stderr
имеют общий предел, а при timeout или переполнении завершается вся группа.

## Внешние инструменты

- **codex CLI**, рабочая модель `gpt-5.6-sol`, запасная `gpt-5.6-terra` — пять
  ролей: сборка карты тем, генерация, проверка, разбор спора и проверка
  осмысленности занятия. Генерация и
  проверка переиспользуются для персональной теории и lesson-вопросов. Модель
  берётся не константой, а `modelForRole(role)`: у каждой роли
  своя переменная окружения (`EDUKATOR_MODEL_CURRICULUM`, `_GENERATE`,
  `_VALIDATE`, `_DISPUTE`, `_INTEGRITY`) с умолчанием в рабочую. Разведение обязательно
  потому, что проверяющий решает задания независимо от генератора: слабый
  проверяющий бракует верные задания, считая расхождение ответов чужой ошибкой.
  Новая точка вызова заводит свою роль в `CODEX_ROLES`/`CODEX_ROLE_ENV`, а не
  зовёт `CODEX_MODEL` напрямую. Недоступность выражается
  `CodexUnavailableError` и обязана пролетать наверх, а не глотаться: на неё у
  воркера свой сценарий (отступ с удвоением паузы). Недоступность — это ровно
  постоянные ошибки запуска (`PERMANENT_SPAWN_ERRORS`: файла нет, прав нет,
  каталог вместо файла) и молчание по сроку; всё остальное с `errno` — беда
  одного вызова (`CodexRunError`). Записав в недоступность, скажем, `E2BIG` от
  слишком длинного промпта, воркер ушёл бы в получасовой отступ на исправной
  модели, бросив остальные темы. Отказ по коду возврата (кончившаяся квота,
  просроченная авторизация) `CodexUnavailableError` тоже **не** даёт — цикл,
  не доливший ни одной голодной темы, ловится отдельно `everyRefillFailed`, и
  это единственный сценарий остановки, общий у воркера и `prefetch`.
  **stdin обязан быть
  закрыт** (`stdio[0] = 'ignore'`, то же что `< /dev/null`), иначе процесс висит
  вечно и молчит. Данные OCR считаются недоверенными: codex запускается во
  временном каталоге с `--sandbox read-only`, без пользовательских правил и
  конфигурации. `shell_tool` и `unified_exec` отключены: read-only запрещает
  запись, но сам по себе не мешает инъекции из PDF читать локальные файлы.
  `--output-schema` не принимает `minItems`, `pattern`,
  `minimum` и родственные ключевые слова — запрос падает `invalid_json_schema`
  ещё до модели.
- **swift + Vision** (только macOS) — OCR сканов. Все три учебника оказались
  сканами, так что в реальности работает именно эта ветка.

## Отладочные мелочи, стоившие времени

- Production-сервер обязан найти `web/dist/index.html` до старта. В dev
  `EDUKATOR_WEB_DEV=1` отключает Fastify static, а `/api` проксирует Vite;
  смешивание режимов либо отдаёт устаревший bundle, либо маскирует отсутствие
  сборки.
- Прокси Vite пишется объектом с `changeOrigin: false`, а не строкой-сокращением
  (`'/api': 'http://localhost:3000'`): сокращение включает `changeOrigin` само и
  подменяет `Host` адресом цели, а изменяющий запрос сверяет с ним `Origin` — в
  dev 403 получал бы каждый вход, выход, ответ ученика и смена PIN. `npm start` и
  e2e одноисточниковые и этого не ловят, поэтому на форму записи есть
  `tests/web-dev-proxy.test.ts`.
- Счётчик параллелизма должен окружать сам вызов codex, а не отдельный воркер
  или маршрут. У воркера общий процессный бюджет на два вызова, у споров — отдельный
  бюджет на один; это осознанный пик в три процесса ради приоритета ответа ученику.
- `runs.total` и `runs.correct` удобны для прогресса, но смысловые итоги забега,
  XP и изменения тем восстанавливаются только из текущих версий
  `attempts WHERE run_id = ? AND is_current = 1`: они — источник истины, а
  сохранённый счётчик не содержит сложности и факта подсказки. Родительское
  активное время, напротив, суммирует `duration_ms` всех версий ответа: на
  исправление ученик тоже потратил время.
- Отсутствие `forecastDelta` у первого снимка — отдельное состояние. Нулевой
  сдвиг означает «предыдущий прогноз был и не изменился»; UI не должен сводить
  эти случаи через `?? 0`.
- Триаж может закончиться раньше 12 ответов: темы или задания исчерпались. Это
  успешный короткий замер, а не `no-task`; клиент должен перейти к финалу.
- `PRAGMA foreign_keys = ON` действует **на соединение**, живёт в
  `openDatabase`; открытие базы мимо него отключает ссылочную целостность.
- `migrate` перечитывает `user_version` **внутри** `transaction(...).immediate()`:
  сервер и `npm run prefetch` открывают базу одновременно, и на чистом чекауте
  оба видят версию 0. Отложенная транзакция повторила бы миграцию поверх готовой
  схемы и упала бы «база без версии содержит объект profile» на исправной базе.
- `JSON.stringify` не экранирует U+0085, U+2028 и U+2029 — это законные знаки
  внутри строки JSON, но для модели такие же переводы строки (см. `dataBlock`).
  `\s` в JS не покрывает U+0085 ни с флагом `u`, ни без него.
- Пустой батч — не исключение. Проверяющий, забраковавший всё, возвращает `[]`,
  так что «долив прошёл без ошибки» и «долив ничего не дал» — разные вещи, и
  причину теме выставляет сам `refillTopic` (иначе `everyRefillFailed` слеп).
- `Number(process.env.X ?? умолчание)`: `??` ловит только незаданную переменную,
  а `X=` даёт `0`. Значения из окружения проверяются явно (`readPort`). У
  `EDUKATOR_DATA_DIR` та же беда с другим концом: пустая строка ушла бы в
  `resolve` и дала текущий рабочий каталог, то есть базы всех детей появились бы
  там, откуда сервер запустили.
- `onClose` в Fastify выполняются в **обратном** порядке регистрации, поэтому
  снятие замка каталога данных регистрируется первым: отработать оно обязано
  последним, уже после закрытия арендаторов и управляющей базы.
- Отказы каркаса точечные: карта тем и `control.db` гасят всё, а испорченная база
  одного ребёнка — только его. Состав маршрутов больше не выбирается на старте
  навсегда: базу открывает реестр по первому обращению, и недоступность
  выражается ответом `unavailable`, а не отсутствием маршрута. `/api/health`
  подробно проверяет `control.db` и сверяет отпечаток файла по **уже открытым**
  детям, не открывая новых: открытие каждой базы на каждый health-запрос — это
  ровно та работа, которой ленивый реестр и избегает.
- Пользовательские адреса объявлены списком (`APP_PAGES`) и покрыты тестом:
  забытый адрес выглядит не поломкой сборки, а мёртвой ссылкой у ребёнка,
  потому что `/join/<token>` уходит в 404 статики, а не на клиента.
- Ребёнок заводится в двух атомарных мирах, поэтому порядок задан явно: строка
  `provisioning` → база во временном файле → `fsync` → `rename` → `ready`.
  Повторный запуск не отказывается вслепую, а продолжает незавершённое; отказ
  стоит только на уже `ready`-ребёнке. `provisionChildDatabase` отказывается
  ещё и когда файл уже на месте, **а** ему передали `source`: доказать, что это
  копия исходной, ему нечем. Решение «это наш прерванный перенос» принимает
  `scripts/adopt-single-user.ts` — строка ребёнка уже есть, `ready` отсеян
  раньше, каталог под замком, — и продолжает **без** `source`. Одного реестра для
  этого мало: детей заводит и экран семьи, тем же протоколом, и совпадение имени
  подсунуло бы переносу пустую заведённую базу. Поэтому продолжение сверяет
  содержимое — забегов и попыток на месте не меньше, чем в оригинале, — и на
  меньшем отказывается: молчаливый успех оставил бы прогресс в оригинале, а
  повторный запуск упёрся бы в отказ по `ready` навсегда. Своя копия этого
  рассуждения внутри `data-dir` превратила бы отказ в молчаливую перезапись.
- Копия базы снимается `VACUUM INTO`, а не `cp`: под WAL часть зафиксированных
  транзакций лежит в спутнике `-wal`, и копия одного файла молча теряет их
  вместе с прогрессом последних занятий.
- `\b` в JS-регулярках только ASCII: `/^глава\b/` не срабатывает никогда,
  граница слова пишется как `(?!\p{L})`.
- Ajv кладёт виновника ошибки в `params`, а не в `message`.
- Ajv под ESM: `default` бывает и самим классом, и вложенным в `.default`.
