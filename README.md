# Edukator

Домашнее приложение для подготовки к вступительным тестам в 7 класс по
русскому, английскому и математике. Бюджет подготовки — около 40 часов, поэтому
приложение не «проходит программу», а ищет пробелы и тратит время ученика
только на них.

Проектная спека: [`docs/superpowers/specs/2026-08-07-edukator-design.md`](docs/superpowers/specs/2026-08-07-edukator-design.md).
Планы этапов: [`docs/plans/20260807-edukator-core.md`](docs/plans/20260807-edukator-core.md) (этап 1),
[`docs/plans/20260807-edukator-generation.md`](docs/plans/20260807-edukator-generation.md) (этап 2).

## Что уже есть

Готов **этап 1 — ядро и данные**: всё, что работает без LLM и без интерфейса.

| Модуль | Назначение |
|---|---|
| `server/db.ts` | SQLite (`better-sqlite3`), схема семи таблиц, идемпотентные миграции, профиль |
| `server/curriculum.ts` | загрузка карты тем из `content/curriculum/*.json`, валидация по JSON Schema, граф тем, синхронизация с `topic_state` |
| `server/normalize.ts` | сверка ответа ученика с эталоном по `answer_format` (`number` / `text` / `choice`) |
| `server/mastery.ts` | модель знаний: `mastery`, `confidence`, пробелы, интервальное повторение |
| `server/scheduler.ts` | приоритет тем и план забегов на день |
| `server/forecast.ts` | прогноз оценки, полоса погрешности, снимки и тренд |
| `scripts/extract-toc.ts` | оглавление учебника из PDF → `content/raw-toc/<subject>.txt` |
| `scripts/toc.ts` | поиск страниц оглавления по плотности пунктов; чистый модуль без ввода-вывода, тестируется на синтетике |
| `scripts/ocr-pdf.swift` | распознавание страниц скана системным Vision (только macOS) |
| `scripts/build-curriculum.ts` | оглавление → карта тем через codex → `content/curriculum/<subject>.json` |

Готов **этап 2 — генерация заданий**: банк заданий наполняется codex заранее,
чтобы ученик не ждал модель.

| Модуль | Назначение |
|---|---|
| `server/codex/client.ts` | общий клиент codex: аргументы, запуск, схема для `--output-schema`, разбор ответа |
| `server/codex/prompt.ts` | промпты генератора, проверяющего и разбора спора; персона из `content/persona.md` |
| `server/codex/task-schema.ts` | разбор батча заданий и инварианты, не выразимые схемой |
| `server/codex/generate.ts` | батч из 5 заданий одним вызовом, до трёх попыток с текстом ошибки в промпте |
| `server/codex/validate.ts` | независимая перепроверка: второй вызов codex видит только условия |
| `server/codex/bank.ts` | `task_bank`: запись, выдача, отпечаток формулировки, остаток по теме |
| `server/codex/worker.ts` | фоновое пополнение очереди по активным темам с отступом при недоступном codex |
| `server/codex/seed-bank.ts` | посевной банк `content/seed-bank/*.json`: загрузка, откат, выгрузка |
| `server/codex/dispute.ts` | разбор спорного ответа моделью |
| `server/session.ts`, `server/routes/session.ts` | занятие: выдача задания, приём ответа, спор |
| `scripts/prefetch.ts` | ручное опережающее наполнение банка и сборка посева |

Впереди: экран забега и триаж (этап 3), дашборд, боссы и диктант (этап 4).

## Установка

Для сервера и тестов нужен Node 26 или новее.

```sh
npm install
```

Сборке карты тем и генерации заданий нужны ещё две вещи; серверу они не нужны,
и без них работает всё остальное:

- **`codex` в `PATH`** с доступом к модели `gpt-5.6-sol` (запасная —
  `gpt-5.6-terra`, см. [Модель по ролям](#модель-по-ролям)) — конвейер проверен
  с codex CLI 0.146.0 (`codex --version`); у других версий может отличаться
  поддержка структурированного вывода. Иначе
  `npm run build-curriculum` падает сразу, не тратя попыток
  (`codex не найден: ожидался исполняемый файл «codex» в PATH`), а
  `npm run prefetch` не пополняет банк и занятие живёт на посевном банке
  (см. [Генерация заданий](#генерация-заданий));
- **macOS с Command Line Tools (`swift`)** — распознавание сканов идёт через
  системный Vision. На другой системе `npm run extract-toc` работает только с
  PDF, у которых есть текстовый слой; чтобы получить внятный отказ вместо
  попытки OCR, передайте `--no-ocr`.

`tsx` и `pdf-parse` — рабочие зависимости, так что сервер и конвейер
(`extract-toc`, `build-curriculum`, `prefetch`) поднимаются и после
`npm install --omit=dev`. Без dev-набора не работают только проверки:
`test`, `coverage`, `typecheck` и `lint`.

npm 11 блокирует install-скрипты зависимостей. Разрешения для `better-sqlite3`
(нативная сборка) и `esbuild` (бинарник) уже зафиксированы в `allowScripts` в
`package.json` — без них не поднимется ни база, ни vitest. Если npm всё же
спросит, ответ даёт `npm approve-scripts`.

## Запуск

```sh
npm run dev     # tsx watch, перезапуск по изменению
npm start       # разовый запуск
```

Сервер слушает `0.0.0.0:3000` (порт переопределяется `PORT`, адрес — нет).
Интерфейса ещё нет — экран забега появится на этапе 3, — но занятие уже доступно
по HTTP:

| Маршрут | Что делает |
|---|---|
| `GET /api/health` | состояние базы, карты тем и занятия |
| `GET /api/session/next` | задание по выбору планировщика, **без** `answer`, `accept[]`, `explain` и `joke` |
| `POST /api/session/answer` | `{ task_id, answer, hint_used?, duration_ms? }` → вердикт, разбор, шутка и новое состояние темы; `answer` длиннее 500 символов — 400 |
| `POST /api/session/dispute` | `{ attempt_id }` → спор в очередь фоновой перепроверки: 202 при заведении, 200 с текущим `status` при повторном нажатии; нецелый или неположительный `attempt_id` — 400, неизвестный — 404 (`attempt-not-found`), уже засчитанная попытка — 400 (`attempt-correct`: спорить не о чем) |

Ответ на задание принимается ровно один раз и только по выданному заданию:
повторный даёт 409, задание из очереди, которое ученику не выдавали, — тоже 409
(`task-not-issued`), а `id`, которого в банке нет вовсе, — 404. Когда предлагать
нечего, `next` перебирает весь план тем и только потом отвечает 503 — 404
читалось бы как ошибка клиента. Одной пустой темы для отказа мало: ответить по
ней ученик не может, состояние её не меняется, и планировщик предложил бы её же
снова; а посев покрывает шесть тем предмета из двадцати с лишним, так что
фиксированное окно из нескольких тем регулярно целиком состоит из пустых.
Тема, задание которой не читается (повреждённый `accept[]`), пропускается с
записью в stderr, а не роняет запрос: строка «выдано, но не отвечено» находится
снова и снова, и пятисотка была бы вечной. Уже выданное задание, которое нечем
сверить, `answer` по той же причине помечает `rejected` и отвечает 409
(`task-defective`), а не 500: причина уходит в stderr, потому что называет
эталонный ответ. Уже выданное, но неотвеченное задание `next` отдаёт
повторно — перезагрузка страницы не должна сжигать очередь. При неподнятой базе
или карте тем все три маршрута отвечают 503 с причиной; подробности — в
`/api/health`. Поломка внутри отвечает 500 с общим текстом: подробности с
локальными путями уходят в stderr, а не в тело ответа.

Подтверждённый спор пересчитывает модель знаний с нуля по всем попыткам темы и
дописывает ответ ученика в `accept[]` задания. Попытка засчитывается всегда, а
вот в `accept[]` ответ попадает не любой: пустая запись, «45 и 46» на числовой
теме, запись со знаком процента и дубль уже имеющегося варианта отбрасываются —
такая запись сделала бы посевной файл предмета неразбираемым навсегда либо
принимала бы долю вместо числа. Разбор идёт фоном и занимает
минуты: вердикт приезжает не в ответе на `dispute`. Если разбор не удался (codex
недоступен, ответ модели не разобрался), спор остаётся `open`, и повторное
нажатие кнопки ставит его на разбор заново. Пока разбор идёт, повторное нажатие
только отдаёт текущий статус: иначе каждое из них поднимало бы ещё один процесс
codex на минуты. Одновременно разбирается не больше **двух** споров (то же
число, что и у воркера): сверх предела спор просто остаётся открытым и попадает
на разбор со следующим нажатием.

Авторизации нет. Привязка к `0.0.0.0` сама по себе не ограничивает приложение
домашней сетью: не публикуйте порт 3000 в интернет, не настраивайте port
forwarding и разрешайте доступ только из доверенной LAN/VPN через firewall.

Проверка живости:

```sh
curl http://localhost:3000/api/health
# {"status":"ok","version":"0.1.0","database":"ok","curriculum":"ok","session":"ok"}
```

### База и резервное копирование

Файл базы — `edukator.db` в корне репозитория. Путь переопределяется переменной
`EDUKATOR_DB`; относительный путь считается от текущего каталога, а родительский
каталог должен существовать:

```sh
EDUKATOR_DB=/absolute/path/edukator.db npm start
```

Схема домигровывается при каждом открытии, отдельной команды миграции нет. База
с более новым `user_version` отвергается: откат приложения не поддерживается.
Health возвращает 503, если база пропала/не открывается, карта тем не загрузилась
или занятие не поднялось, и не создаёт новую пустую базу на месте пропавшей.
Ответ содержит только стабильные поля `status`, `version`, `database`,
`curriculum` и `session`; подробности с локальными путями пишутся в stderr. База
проверяется заново на каждый запрос. Карта загружается один раз при старте,
поэтому после её ремонта сервер нужно перезапустить. `session` тоже решается один
раз: маршруты занятия выбираются при старте, и поднявшаяся позже база их не
вернёт — поэтому `session: "error"` держит health красным, хотя `database` уже
`ok`. Это честнее зелёного статуса над процессом, который на `/api/session/*`
до перезапуска отдаёт 503.

Для резервной копии остановите сервер и копируйте `.db` вместе с соседними
`-wal`/`-shm`, либо используйте штатный SQLite backup / `VACUUM INTO` на живой
базе. Копирование только `.db` при активном WAL может потерять последние записи.

Профиль на этапе 1 настраивается только программно через `writeProfile` из
`server/db.ts`; публичного CLI/API для имени, интересов, даты экзамена и имени
напарника пока нет. Не правьте профиль SQL вручную: эта функция валидирует дату
и сериализует интересы. Пользовательский экран появится на следующем UI-этапе.

### Программное использование ядра

Базу открывают только через `openDatabase`, затем загружают карту через
`loadCurriculum` и синхронизируют её с `topic_state`. `checkAnswer` не пишет в
базу. `recordAttempt` атомарно обновляет только состояние освоения темы; строку
истории в `attempts` с `task_id` и `run_id` обязан записать вызывающий сценарий.
`planFromDatabase` читает профиль и начатые забеги, а `recordForecasts` пишет
общий и предметные снимки одной транзакцией. До появления UI дата экзамена
задаётся вызовом `writeProfile(db, { examDate: 'YYYY-MM-DD' })`.

## Проверки

```sh
npm test        # vitest, все tests/**/*.test.ts
npm run coverage
npm run typecheck
npm run lint
```

`coverage` держит порог 80% (строки, ветви, функции) **пофайлово** на четырёх
группах: ядро (`normalize`, `mastery`, `scheduler`, `forecast`), занятие
(`session`, `curriculum`, `db`, `json-schema`), маршруты (`server/routes/*.ts`)
и генерация (`server/codex/*.ts`), плюс каркас — `index`, `run-child`,
`atomic-write`. Пороги висят именно на них: всё это детерминировано (внешние
процессы подменяются через `run`/`produce`/`review`), а дефект тихо портит
учебный план, не роняя ни одного теста. Пофайлово, а не в среднем по группе:
иначе один модуль мог бы просесть до нуля, пока общая цифра держится соседями.
Скрипты извлечения PDF и сборки карты завязаны на сканы и на codex, общий порог
по репозиторию был бы враньём.

## Сборка карты тем

Карты трёх предметов уже лежат в `content/curriculum/` и в репозитории. Заново
собирать их нужно, только если меняются учебники или состав тем.

Конвейер из двух шагов.

**1. Оглавление учебника из PDF**

```sh
npm run extract-toc -- --subject math --pdf ~/Downloads/merzljak-6.pdf
```

| Флаг | Обязателен / значение по умолчанию | Смысл |
|---|---|---|
| `--subject` | да | `math`, `russian` или `english` |
| `--pdf` | да | путь к учебнику |
| `--pages` | поиск автоматически | страницы PDF с единицы, не печатные номера; `12` или `12-15`, диапазон обязан лежать внутри файла и отключает эвристику |
| `--scan` | `15` | положительное число страниц с каждого края |
| `--no-ocr` | OCR автоматический | запретить Vision OCR; с `--pages` также явно доверяет даже короткому текстовому слою |
| `--out` | `content/raw-toc` | каталог результата |

Результат перезаписывает `<out>/<subject>.txt`. Сначала проверяется найденное
оглавление в текстовом слое; OCR запускается, если подходящих страниц нет и хотя
бы одна из просмотренных страниц имеет слишком бедный слой. Это правило
действует и для ручного диапазона: богатый текст соседней страницы не скрывает
скан оглавления, а один номер страницы или штамп не считается оглавлением.
Чтобы намеренно сохранить короткий текстовый слой без OCR, укажите
`--pages ... --no-ocr`.

**2. Карта тем через codex**

```sh
npm run build-curriculum -- --subject math
```

| Флаг | Обязателен / значение по умолчанию | Смысл |
|---|---|---|
| `--subject` | да | `math`, `russian` или `english` |
| `--toc` | `content/raw-toc/<subject>.txt` | входное оглавление |
| `--out` | `content/curriculum` | каталог карты; рабочий `<subject>.json` атомарно заменяется только после валидации |
| `--attempts` | `3` | положительное целое число попыток |
| `--model` | модель роли `curriculum` | модель codex |

Скрипт требует 20-25 тем на предмет, прогоняет ответ через тот же валидатор,
что и файл из репозитория (схема, дубли `id`, ссылки в `prereqs`, циклы,
предпосылки вне экзамена, число тем в пределах 15-30), и при провале уходит на
следующую попытку, дописав текст
ошибки в промпт. После трёх неудач падает с отчётом по всем попыткам. В промпт
дописывается только то, что провалила сама модель: сорванный запуск codex
(ненулевой код возврата, не записанный ответ) идёт в отчёт, но не в промпт —
это диагностика CLI, а не замечание к ответу.

Распознанное оглавление уходит в промпт блоком JSON и режется по длине: это
недоверенный текст со скана, и текстовыми разделителями он умеет закрыть свой
раздел промпта и открыть собственный.

### Формат темы

Карты правятся руками, поэтому вот из чего состоит тема. Источник правды —
`schemas/curriculum.json`, файл проверяется тем же валидатором, что и ответ
модели (`npm test` прогоняет приёмочную проверку всех трёх карт).

| Поле | Значение |
|---|---|
| `id` | `<subject>.<латиницей-через-дефис>`. Менять нельзя: на него ссылаются `topic_state`, задания и попытки, смена `id` теряет накопленный прогресс |
| `subject` | `math` / `russian` / `english`, обязан совпадать с `subject` файла |
| `title` | название обычными словами — попадёт в дашборд родителей |
| `exam_weight` | 0-3, вероятность встретиться на вступительном. Главный рычаг приоритизации; при `< 1` тема не идёт ни в прогноз, ни в отставание предмета, а при `0` не попадает и в план |
| `difficulty` | 1-3, базовая сложность |
| `prereqs` | массив `id` тем того же файла, без циклов и дублей. Пока не каждая предпосылка достигла `mastery` 0.6, приоритет темы уменьшается мягким множителем `max(0.2, среднее(min(1, mastery / 0.6)))`, но не обнуляется. Предпосылкой не может быть тема с `exam_weight` 0: сама она никогда не попадёт в план |
| `answer_format` | `number` / `text` / `choice` — выбирает ветвь нормализатора |
| `prompt_seed` | как генерировать задания: что спрашивать, какие числа и слова брать, 2-3 примера формулировок целиком |

При `answer_format: number` формулировки в `prompt_seed` обязаны требовать **ровно
одно число**. «Найдите оба числа», «расположите в порядке возрастания»,
«разложите на простые множители», «запишите формулу», ответ вида `3:4` и ответы
словами дают ноль или несколько чисел, а такой эталон нормализатор считает
дефектом задания и падает — не в тестах, а на живом ответе ученика. Либо
переформулируйте вопрос под одно число, либо ставьте теме `text`. Смешанные
числа (`1 2/3`) и обыкновенные дроби (`3/4`) считаются одним числом и
допустимы.

Синхронизация карты ничего не удаляет. Удалённый или переименованный `id`
оставляет осиротевшую строку `topic_state` и предупреждение в stderr, но health
остаётся зелёным; возврат старого `id` снова подключит сохранённый прогресс.
Переименование поэтому оформляют как явную миграцию всех ссылок, а не как
обычную правку JSON.

## Генерация заданий

Задача этапа сформулирована двумя запретами: **ученик никогда не видит спиннер и
никогда не получает кривое задание**. Первое обеспечивает опережающая генерация,
второе — независимая перепроверка каждого задания вторым вызовом модели.

```
планировщик → активные темы → генератор (codex, батч 5)
                            → проверяющий (codex, видит только условия)
                            → сверка ответов через normalize.ts
                            → task_bank
```

Батч из 5 заданий с подсказкой, разбором и шуткой занимает у `gpt-5.6-sol`
около 29 секунд и покрывает 5-10 минут решения — поэтому очередь успевает
наполняться, пока ученик занимается, но только если её начали греть заранее.

### Модель по ролям

codex зовётся из четырёх мест, и модель задаётся на каждое отдельно. Разводить
роли приходится потому, что проверяющий решает задания независимо от генератора:
если он слабее, расхождение ответов он списывает на ошибку генератора и бракует
верные задания.

| Переменная | Роль | Умолчание |
|---|---|---|
| `EDUKATOR_MODEL_GENERATE` | генератор заданий | `gpt-5.6-sol` |
| `EDUKATOR_MODEL_VALIDATE` | проверяющий | `gpt-5.6-sol` |
| `EDUKATOR_MODEL_DISPUTE` | разбор спора | `gpt-5.6-sol` |
| `EDUKATOR_MODEL_CURRICULUM` | сборка карты тем | `gpt-5.6-sol` |

Пустая переменная считается незаданной. Запасная модель — `gpt-5.6-terra`,
автоматического отката на неё нет: её выбирают руками этими же переменными или
флагом `--model`. Флаг сильнее переменной и в `prefetch` накрывает обе роли
сразу — генератора и проверяющего.

### Опережающее наполнение

```sh
npm run prefetch                              # погреть ближайшие темы плана
npm run prefetch -- --topics 12 --target 10   # шире и глубже
npm run prefetch -- --target 10 --threshold 10  # добрать и уже тёплые темы
npm run prefetch -- --export                  # выгрузить банк в посевные файлы
```

| Флаг | Значение по умолчанию | Смысл |
|---|---|---|
| `--topics` | `3` | сколько ближайших тем плана греть |
| `--target` | `8` | до какого запаса заданий доливать тему |
| `--threshold` | `4`, но не выше `--target` | остаток, ниже которого тема доливается |
| `--batches` | `4` | потолок батчей на тему за цикл |
| `--cycles` | `1` | сколько циклов подряд; между ними план пересчитывается |
| `--model` | модели ролей `generate` и `validate` | одна модель сразу на генератор и на проверяющего; чтобы развести их, задавайте `EDUKATOR_MODEL_*` |
| `--export` | выключено | выгрузить содержимое банка в посевные файлы |
| `--out` | `content/seed-bank` | куда выгружать посев |
| `--seed-dir` | `content/seed-bank` | откуда подгружать посев перед наполнением |
| `--db` | `edukator.db` (или `EDUKATOR_DB`) | база |
| `--curriculum` | `content/curriculum` | карта тем |

Тема доливается, только пока её остаток ниже порога, поэтому один поднятый
`--target` уже тёплые темы глубже не копает — поднимайте вместе с ним и
`--threshold`. Прогон, в котором codex не запустился, не долилась ни одна
голодная тема либо сорвалась выгрузка посева (`--export`: посев предмета не
прочитался, снимок не собрался, файл не записался), возвращает код 1: `prefetch`
зовут из `&&`-цепочек, и «0 новых заданий» с нулём на выходе там неотличимо от
«всё уже тёплое». Цикл, в котором не долилась ни одна голодная тема, обрывает и
остальные циклы: следующий пошёл бы по тем же темам с тем же результатом.

Тот же цикл умеет крутиться фоном: `startWorker` из `server/codex/worker.ts`
держит **не менее 8** провалидированных заданий на активную тему, запускает
долив при падении **ниже 4** и не ведёт больше **двух** тем одновременно (предел
считается по темам, а не по вызовам: пополнение темы — это генератор и
проверяющий подряд). Активные темы берутся у планировщика, плюс темы уже начатых
сегодня забегов: планировщик считает их использованными и больше не предложит, а
задания прямо сейчас берутся именно из них. В сервер воркер пока не включён —
до появления экрана забега очередь греется руками через `npm run prefetch`.

### Посевной банк

`content/seed-bank/{math,russian,english}.json` — снимок банка, лежащий в
репозитории: math 52 задания, russian 57, english 47, по 6 тем на предмет. Он
закрывает два случая: первый запуск, когда база пуста, и откат, когда codex
недоступен и воркеру нечем пополнить очередь.

Посев заливается один раз за старт сервера и ещё раз лениво — когда очередь темы
оказалась пуста, `takeTaskOrSeed` дозаливает посев по предмету этой темы и
повторяет выдачу. Отметки «посев загружен» нет намеренно: повтор отсекается тем
же отпечатком формулировки, что и дубли генератора, поэтому дописать в посевной
файл новую тему можно в любой момент, а флаг разошёлся бы с содержимым базы.

Порча посевного файла занятие не роняет ни при старте, ни посреди него: причина
уходит в stderr, а тема выглядит просто пустой — что и есть правда.

Посев проходит через тот же `parseTaskBatch`, что и ответ модели: файл в
репозитории — такой же непроверенный текст, просто сгенерированный раньше. Тема
вне карты роняет разбор, а не молча пропускает задание.

Обновляется посев выгрузкой из банка:

```sh
npm run prefetch -- --topics 18 --cycles 3 --export
```

Выгрузка берёт задания темы, включая выданные, а порядок тем — из карты: иначе
каждый экспорт давал бы бессмысленный диф. Не берутся только отбракованные
(`rejected`): негодным их пометило само занятие, и вернувшись в посев такое
задание либо снова уехало бы ученику, либо уронило бы разбор файла и оставило бы
без посева весь предмет.

Пишутся посевные файлы через соседний временный, как и карта тем: оборванная на
середине запись оставила бы вместо снимка битый JSON.

### Когда codex недоступен

Ничего не падает. Воркер ловит `CodexUnavailableError`, пишет в лог и уходит на
паузу, удваивающуюся с каждым подряд идущим отказом: минута, две, четыре — до
получаса. Так же он поступает с циклом, в котором была хоть одна голодная тема и
ни одна не долилась: `CodexUnavailableError` покрывает не всякий отказ модели —
процесс, стартовавший и вышедший с ненулевым кодом (просроченная авторизация,
исчерпанная квота), приезжает обычной ошибкой, и без этой проверки воркер
запускал бы codex по каждой голодной теме раз в минуту вечно. Отказ одной темы
из нескольких отступа не включает: очередь всё-таки греется. Ручной `prefetch`
цикл не повторяет: ждать возвращения codex в
интерактивном запуске незачем. Задание ученику всё равно выдаётся — из очереди,
а когда она пуста, из посевного банка. Спорный ответ в это время остаётся
открытым и разберётся следующей попыткой, а не закрывается отказом.

### Формат задания и требования к `accept[]`

Источник правды — `schemas/tasks.json`; инварианты, которые схема выразить не
может, проверяет `server/codex/task-schema.ts`. Через него проходит и ответ
модели, и посевной файл.

| Поле | Значение |
|---|---|
| `question` | условие целиком, без ответа и без подсказки; один вопрос |
| `answer` | эталон в самой короткой записи; для числовой темы — ровно одно число без пояснений |
| `accept` | равноправные записи того же ответа, включая `answer` |
| `hint` | направляет к решению и не содержит ответа |
| `explain` | разбор по шагам, показывается после ответа |
| `joke` | короткая шутка напарника в тон подростку |
| `difficulty` | 1, 2 или 3 |

Требования к `accept[]`, каждое со своей причиной:

- **непуст и содержит `answer`** — иначе эталон не сойдётся сам с собой;
- **без дублей**, причём повтор ищется нормализацией того же формата, которым
  потом сверяется ответ ученика: две записи, неотличимые для нормализатора, —
  мусор, а не варианты;
- **при `answer_format: number` в записи не больше одного числа.** «45 или 46»
  неоднозначно и отвергается, а вот словесная форма без чисел («сорок пять»)
  допустима: она сверяется как текст. Запретить её нельзя — разбор спора
  дописывает в `accept[]` подтверждённый ответ ученика как есть, а выгруженный
  посевной файл читается обратно этим же разбором, и запрет ломал бы задание
  навсегда после первого же спора. Сам `answer` при этом обязан читаться как
  ровно одно число, и проверка идёт до сверки `answer` с `accept[]` именно
  поэтому: эталон без числа уронил бы нормализатор. Генератору словесные записи
  всё равно запрещены промптом — они нужны только как след спора;
- **при `answer_format: number` в записи нет знака процента.** «40%»
  нормализатор читает как долю 0,4, так что рядом с ответом «40» такая запись
  засчитывала бы ответ, ошибочный ровно в сто раз, и поднимала бы за него
  `mastery`. Ученику она при этом не нужна: два прочтения «40%» разворачиваются
  только для ответа ученика, и написанное им «40%» проходит по самому `answer`.
  Запрет действует и на разбор спора — иначе дыра открывалась бы уже в рабочей
  базе, а не при генерации;
- **`hint` не содержит `answer`** — совпадение ищется по границе слова, но не
  через `\b` (она в JS только ASCII, а ответы бывают русскими словами), поэтому
  подсказка «начни с 450 монет» не считается раскрывающей ответ 45.

Практически `accept[]` — это главное место, где решается, засчитается ли верный
ответ ученика. Наполнять его нужно всеми записями, которые ребёнок реально
наберёт: сокращениями («несов. вид» рядом с «несовершенный вид»), номером без
слова («II» рядом с «II спряжение»), словом и цифрой. Числовые вольности
нормализатор берёт на себя сам — юникодный минус, запятую как разделитель,
пробел между разрядами, дробь, — а текстовые не берёт никто.

### Проверка сгенерированного

Проверяющий получает **только условия**: без ответов, подсказок и разборов.
Он решает каждое задание сам и отдельно оценивает четыре вещи — условие
однозначно, ситуация не натянута, тема заявленная, содержание уместно подростку.
Ответ проверяющего сверяется с эталоном генератора нормализатором, а не строкой:
«−45» и «-45 монет» — один и тот же ответ. Расхождение ответов или любая
проваленная оценка отправляют задание в отбраковку с записанной причиной.

Персоны и профиля ученика в промпте проверяющего намеренно нет: общий с
генератором контекст толкает проверяющего согласиться с уже написанным.

## Подводные камни

Здесь собрано то, что стоило времени при реализации и не выводится из кода.

**codex висит без `< /dev/null`.** Вызов обязан закрывать stdin, иначе процесс
ждёт ввода. OCR ограничен 5 минутами, каждый вызов codex — 10 минутами, а общий
stdout+stderr процесса — 1 МиБ. `--attempts 3` поэтому допускает до 30 минут
работы модели. CLI-флагов для этих лимитов пока нет. Зависший процесс и вся его
группа завершаются; это проверяется исполняемыми заглушками.
Полная форма вызова:

```sh
codex exec --ephemeral --ignore-user-config --ignore-rules \
  --skip-git-repo-check --disable shell_tool --disable unified_exec \
  --sandbox read-only --cd <временный-каталог> \
  -m gpt-5.6-sol \
  --output-schema <schema> -o <out> "<промпт>" < /dev/null
```

**`--output-schema` не принимает половину JSON Schema.** Запрос падает с
`invalid_json_schema` ещё до обращения к модели на `uniqueItems`, `minItems`,
`pattern`, `minLength`, `minimum`/`maximum` и родственных ключевых словах.
Поэтому в рабочий каталог кладётся очищенная копия схемы, а ограничения не
теряются: их проверяет разбор ответа, диапазоны продублированы словами в
`description` и в промпте. Чистка (`codexOutputSchema`) общая для всех четырёх
схем — `curriculum.json`, `tasks.json`, `verdicts.json`, `dispute.json`, — и
рукописной копии ни одной из них в коде нет. Режет она только ключевые слова:
ключи под `properties` — это имена полей данных, и поле, названное `pattern` или
`minimum`, осталось бы в `required`, сделав схему невыполнимой.

**Корень схемы — объект, а не массив.** Структурированный вывод допускает в
корне только объект, поэтому и карта, и батч заданий имеют вид
`{ ..., items[] }`, а не голый массив.

**Все три учебника — сканы без текстового слоя.** `pdf-parse` вытаскивает из
818 страниц ноль символов, так что добавлен откат в OCR:
`scripts/ocr-pdf.swift` рендерит страницу через PDFKit и распознаёт системным
Vision (`ru-RU` + `en-US`). Vision выбран потому, что он уже есть в macOS,
знает русский и не требует ни установки, ни языковых моделей; плата — эта ветка
работает только на macOS. `pdf-parse` остался первой попыткой: для PDF с
текстовым слоем OCR не запускается.

**OCR читает оглавление по колонкам.** Сначала идут все названия, потом
отдельным блоком все номера страниц, а «§» часто распознаётся как «$».
Эвристика «название … номер страницы» на таком тексте не работает, поэтому
пункт опознаётся тремя способами: отточие с номером в конце строки, маркер
раздела в начале строки и голый номер страницы. Голые номера засчитываются
только там, где уже есть хотя бы три названия, — иначе страница «Ответы к
упражнениям» выглядит идеальным оглавлением.

**Оглавление бывает в конце книги** (математика — с. 333, русский — с. 314-318,
английский — с. 3), а OCR страницы стоит около секунды. Поэтому просматриваются
не все страницы, а по 15 с каждого края.

**`\b` в JS работает только с ASCII.** `/^глава\b/` не находит границу после
кириллицы и не срабатывает никогда. Граница слова выражена через `(?!\p{L})`.

**Внешние ключи SQLite включаются на каждом соединении.** `PRAGMA
foreign_keys = ON` живёт в `openDatabase`, а не в схеме; открытие базы мимо
`openDatabase` молча отключает всю ссылочную целостность.

**Ajv кладёт виновника ошибки в `params`, а не в `message`.** Текст ошибки
собирается из обоих — иначе «must NOT have additional properties» не говорит,
какое поле лишнее.

**Темы с многочастным текстовым ответом дают вдвое меньше батча.** Проверяющий
массово отбраковывает разборы, где ответ состоит из нескольких частей: он пишет
«несовершенный вид», генератор — «несов. вид», и это честное расхождение —
ученик наберёт как придётся. Кодом это не лечится, лечится составом `accept[]` и
формулировкой `prompt_seed`. Половину потерь снял переход на `gpt-5.6-sol`: он
сам перечисляет сокращения в `accept[]`. Остальное по-прежнему на составе
посева — закладывайтесь на такой выход при его сборке.

**Порог долива считается по остатку, а не по запасу.** Тему с 4-5 заданиями
воркер не трогает вовсе, поэтому «догнать предмет до 30 заданий» повторными
циклами по тем же темам не выйдет: цикл честно решит, что делать нечего. План
берут шире (`--topics 18`), и добор идёт новыми темами.

**Отпечаток формулировки обязан различать числа и знаки действия.** Он
нормализует пробелы и регистр, но не цифры и не знаки: склеив «2+2» и «3+5» — или
«4800 : 16 + 37 · 25» и «4800 · 16 - 37 : 25», отличающиеся только знаками, —
банк отверг бы всю тему как дубли после первого же задания. Синонимы одного
знака («·», «×», «*») при этом сводятся к одной записи.

**Дубли отсекаются базой, а не чтением перед вставкой.** Воркер пополняет две
темы одновременно, и между «прочитали отпечатки» и «записали» пролезал бы тот же
вопрос. Вставка идёт `ON CONFLICT DO NOTHING`, выдача — одним
`UPDATE ... RETURNING` по той же причине: выбор и пометка врозь дали бы двум
забегам одно задание.

## Решения ядра

**Юникодный минус.** `−45` и `-45` — одно и то же число; туда же запятая как
десятичный разделитель, дробь `a/b` (тема `math.common-fractions` объявлена
как `number`, иначе «3/4» не сошлось бы с «0,75») и пробел между разрядами
(«45 000» — одно число, но «12 3» — два). Причина отказа возвращается отдельным
полем (`mismatch`, `empty`, `no-number`, `ambiguous-number`): разбору спора
через LLM на этапе 3 нужно различать «не то число» и «в ответе их два».
Неоднозначный эталон в задании — дефект банка, а не ошибка ученика: проверка
падает с внятной ошибкой и делается до проверки ответа.

Ответ со знаком процента читается двояко: «45%» подходит и к эталону `0.45`, и к
эталону `45`. Эталон темы `math.percent` записан самим числом («Сколько
процентов класса составляют девочки?» — «40»), и одно только деление на сто
засчитывало бы верный ответ неверным. Обратной симметрии нет намеренно: голое
«50» при эталоне `0.5` остаётся другим числом, а не второй записью того же.
Из-за этой односторонности сам эталон числовой темы со знаком процента запрещён
(`parseTaskBatch`): «40%» в `answer` нормализатор прочёл бы как долю 0,4, и
ученик, написавший требуемое формой ответа «40», получил бы незачёт на верном
ответе. Промпт генератора требует голого числа.
Выбор (`choice`) сверяется знак в знак — метка «A» и вариант «A) Work in pairs»
обязаны остаться разными записями, — но регистр снимается: ученик вводит ответ
руками. Кириллические двойники латинских букв при этом не сводятся: «В» списка
«А, Б, В» выглядит ровно как «B» списка «A, B, C», и замена засчитывала бы
соседний вариант. Поэтому обе буквы метки-двойника обязаны лежать в `accept[]`
самого задания: русское задание с метками `A)`–`D)` ученик набирает в русской
раскладке, и «А» (U+0410) иначе считалось бы ошибкой. Промпт генератора этого
требует, посев на такие метки уже дополнен.

**Уверенность затухает непрерывно.** Хранимая `confidence` свежа только на
момент `last_seen`, текущее значение считает `confidenceAt(state, now)`.
Побочный эффект: после долгого простоя тема выпадает из «пробелов» — данных о
ней фактически больше нет.

**Подсказка ослабляет только рост.** Неверный ответ с подсказкой падает на
общих основаниях: подсказали, и всё равно мимо — это худший сигнал, а не
смягчающий.

**Предметы не чередуются строго.** Строгое чередование по максимуму отставания
выбрасывает третий предмет из плана совсем. Спрос предмета считается как
`SUBJECT_FLOOR + deficit` и делится на число уже назначенных ему забегов: при
отставании 1.0 / 0.5 / 0.2 план из шести забегов даёт 3 / 2 / 1 без двух
забегов подряд по одному предмету.

**«Считать не из чего» — это `null`, а не двойка.** Карта без тем с
`exam_weight ≥ 1` означает «неизвестно»; оценка 2.0 была бы утверждением о
ребёнке, которого никто не проверял.

## Решения генерации

**Всё, что пришло не от нас, уходит в промпт блоком JSON.** Интересы вводит
человек, прошлые формулировки и замечания неудачной попытки приходят от модели —
ни то, ни другое не должно уметь открыть собственный раздел промпта и
переопределить инструкции. Разделы промпта пишет только код.

**Персона — один файл на всё приложение.** `content/persona.md` читается до
первого вызова codex: его отсутствие — ошибка настройки, и узнать о ней дешевле
сразу, чем через полминуты работы модели. Промахивается тон напарника — правится
это в одном месте.

**Задание уезжает в браузер без ответа.** В выдаче нет `answer` и `accept[]` —
и заодно нет `explain` и `joke`: разбор пересказывает решение целиком, то есть
содержит тот же ответ другими словами. Всё это ученик получает ответом на
задание.

**Подтверждённый спор пересчитывает модель заново.** Обратным сдвигом это не
чинится: `mastery` меняется цепочкой, и после спорной попытки успели пройти
другие. Источник истины пересчёта — таблица `attempts`.

**Вызов модели никогда не идёт внутри транзакции.** Он занимает минуты и под WAL
держал бы запись. Спор перечитывается уже под записью: параллельный разбор мог
закрыть его, и второй вердикт удвоил бы `accept[]`.

## Что делает человек

Автоматические тесты проверяют структуру карты тем и инварианты заданий, но не
их содержание. Ниже — то, что остаётся человеку перед этапом 3.

**Карта тем.** Прочитать `content/curriculum/*.json` и убедиться, что темы
соответствуют программе 6 класса, а `prompt_seed` даёт осмысленные задания.
Туда же — правка `exam_weight` по известным слабым местам конкретного ребёнка
и точная дата экзамена в профиле: от неё считается рост срочности тем.
Отдельно — прогнать планировщик на заполненной карте и вручную проверить первые
10 тем. Жёсткий `prereqs_ready` уже заменён мягким множителем; остаётся решить,
как поступить с тяжёлыми темами, которые не помещаются в 40-часовой бюджет при
50-60% верных ответов. Если формула меняется, сначала обновляется утверждённая
спека.

**Выборка заданий.** Прочитать по 10 заданий каждого предмета из
`content/seed-bank/` и оценить: условия осмысленны, юмор попадает в возраст,
разборы понятны. Проверяющий ловит расхождение ответов и натянутые ситуации, но
вкус проверить не может. Промахивается тон — правится `content/persona.md`.

**Профиль.** Указать имя ребёнка и интересы. До этого генерация работает на
нейтральном умолчании (`видеоигры`, `ютуб и стримы`, `школьные будни`) и сюжеты
будут пресными — а это единственное, что реально отличает «задачи из его мира»
от обычного задачника.
